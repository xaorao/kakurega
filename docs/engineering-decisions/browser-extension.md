# Browser extension (registry N67; Milestone III)

## Target experience
Select text on any page, right-click, choose "Send selection to Kakurega"; it appears in Kakurega as a suggestion marked untrusted, with only the site's origin as its source. Nothing is saved until the owner accepts it. The extension asks the browser for almost nothing and can do almost nothing, so installing it is not a leap of trust.

## References and what was read
- Ghast extension 0.1.9 (no licence file: ideas only; `private-ai/ghast-ai/_shipped`): its manifest was read. It requests `tabs`, `scripting`, `nativeMessaging`, `identity`, `bookmarks`, `notifications`, `unlimitedStorage`, about 30 host permissions including `localhost` and `127.0.0.1`, and injects a content script into 15 sites; its background script is 6.9 MB. Source is minified and was not read. What it teaches: the permission surface of a capable extension is large and every item is trust the user must extend. We copy none of it.
- Not studied: other extensions' source, Chrome's extension security review guidance beyond the manifest reference. NOT VERIFIED: Chrome Web Store review requirements.

## Decision
The smallest useful extension: permissions `contextMenus` and `storage` only; host permission `http://127.0.0.1/*` only; no content scripts, no `activeTab`, no `tabs`, no `scripting`, no remote code, no `externally_connectable`. The selection text and page URL come from the context-menu event itself, so the extension never reads a page it was not told to send from.

The service side is a separate channel `/ext/*`: a bearer token minted by a one-time pairing code that the owner generates (`kaku extension pair`), pinned to the extension's own origin, refused if a cookie or any non-extension Origin is present, rate-limited on wrong codes, and able to do exactly two things: report counts and queue an untrusted memory suggestion (text up to 2000 characters, origin only, secrets refused). The owner accepts or dismisses in the Memory screen. Pairing again replaces the old extension; the owner can revoke at any time.

## Quality criteria and evidence
`cargo test -p kk-service --test flow sv18` (pairing, origin pinning, token, cookies, lockout, validation, owner acceptance, restart, revoke; seven deliberate breaks each failed it), `cd apps/extension && node --test test/*.test.mjs` (10 tests: exact permission set, content security policy, no eval or inline code, loopback only, pure logic, background wiring with a stubbed browser), `node tests/e2e/extension.mjs` (real Chrome: the extension loads, pairs, queues, the owner reviews it in the workspace, a hostile web page cannot read or plant anything, disconnect and revoke).

## Not covered
The native context-menu click itself (no automation hook; the handler is tested with a stubbed browser and the same capture module is driven from an extension page against the real service); Firefox and Safari; Chrome Web Store packaging and review; an extension update path; capturing page content other than a selection; any use on pages loaded over a non-loopback service (there is none by design).

## Review against Chrome's extension security guidance (ledger F-X6)
- Guidance read by me, from the live pages: "Improving security in Manifest V3" (developer.chrome.com/docs/extensions/develop/migrate/improve-security): the first part, no `eval`/`new Function`/`executeScript` of strings, no remotely hosted code, bundle libraries; and "Stay secure" (.../security-privacy/stay-secure) up to and including "Use content scripts carefully" (about the first 5,000 characters): protect the developer account with two-factor sign-in, never use HTTP, request minimal permissions and host permissions, limit manifest fields, restrict `externally_connectable`, keep web-accessible resources to a minimum, set an explicit content security policy, avoid `document.write` and `innerHTML`, use content scripts carefully. NOT READ: the rest of "Stay secure" and the Chrome Web Store program policies (the review before a store listing needs them).
- Checked against `apps/extension`, each item with its evidence: permissions are `contextMenus` and `storage` only and the one host permission is `http://127.0.0.1/*` (tests ex06, which also bans `tabs`, `scripting`, `activeTab`, `cookies`, `webRequest` and others); no `externally_connectable`, `web_accessible_resources`, `content_scripts` or `nativeMessaging` (ex06); an explicit policy `script-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` with no `unsafe-inline`, `unsafe-eval` or remote source (ex07); no `eval`, `new Function`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `importScripts`, inline script or inline handler, and every URL in the sources is the loopback address (ex08); the popup loads only `popup.css` and `popup.js` (ex09). The service worker registers only a context-menu click handler: it has no `runtime.onMessage` or `onMessageExternal` handler, so there is no sender to check. Requests use `credentials: "omit"`, `cache: "no-store"` and `redirect: "error"` (lib.js).
- One departure from the guidance, on purpose: "never use HTTP". The extension speaks plain HTTP, but only to the program on the same computer (`127.0.0.1`), where there is no network path to eavesdrop on and a certificate would add nothing; Chrome treats loopback as a secure context. Every other address is refused by the host permission and by test ex08.
- Result: no change to the extension was needed; the guidance review is now recorded. Owed before a store submission: the rest of "Stay secure", the program policies, and two-factor sign-in on the publisher account (a person's step: HUMAN.md).

## Chrome Web Store policies and the rest of "Stay secure": read, checked, and the missing text written (ledger F-X6)
- Read by me from the live pages (fetched through the reader proxy): "Stay secure" in full (9,502 characters; the part after "Use content scripts carefully" is "Register and sanitize inputs"); the Chrome Web Store **Program Policies** page (39 KB): Privacy Policy, Limited Use, Use of Permissions, Disclosure Requirements, Handling Requirements, Deceptive Installation Tactics, Misleading or Unexpected Behavior, Spam and Abuse, Quality Guidelines, Listing Requirements, Minimum Functionality, Code Readability, API Use, Additional Requirements for Manifest V3 and 2-Step Verification; the **User Data FAQ** questions 2, 3, 6, 14, 15 and 16; the Limited Use page was fetched and not read beyond the policy page's summary of it. NOT READ: the sections that do not describe this extension (mature, hateful, regulated and prohibited content, impersonation, payments, ads and affiliate ads, Chrome Apps), the dashboard "privacy fields" page, and every FAQ other than the user-data one.
- What the code does (read in full: `manifest.json`, `capture.js`, `lib.js`, `background.js`): on the user's choice of the context-menu item it sends the selected text (at most 2,000 characters; text that looks like a secret is refused first) and the site's origin only (scheme and host, never the path, query or fragment) to `http://127.0.0.1:<port>/ext/capture` with a bearer pairing token, and saves only the port and the token in `chrome.storage.local`.
- Each rule against the extension: single purpose, narrow and clear (send a selection to the local workspace); narrowest permissions (`contextMenus`, `storage`, one loopback host; no future-proofing); no remote code or `eval` (ex07, ex08, ex15) and no obfuscation (plain source files, no build step), so the whole behaviour is readable from the package as the MV3 rule requires; no message listeners and no content scripts, so "Register and sanitize inputs" and "Use content scripts carefully" have nothing to apply to; nothing is sent on a user's behalf without confirmation (the capture waits in Kakurega until the owner accepts it); no ads, payments, notifications, installation tactics or bundled offers.
- The "never use HTTP" departure recorded above is covered by the User Data FAQ itself (question 16: the encryption requirement does not apply to transmissions between an extension and a native program on the same computer). INFERRED, not stated by the policy: that the local Kakurega service counts as such a program.
- **Gap found and closed: the policy and disclosure text did not exist.** Questions 3 and 14 say disclosure and a privacy policy are required even when data is only handled locally, and clipping content from a page the user visits counts as handling user data (question 2). Written from the code: `docs/extension-privacy-policy.md` (what is collected and when, where it goes, what happens afterwards, use and sharing, security, the user's choices, changes, contact via the store page) and `docs/extension-store-listing.md` (single purpose, the manifest description, the detailed description with the disclosure, the permission justifications and the privacy-practices answers).
- Evidence: extension tests ex11 to ex15 (the limit in both documents is the code's `MAX_SELECTION`; the short description is the manifest's and fits the 132-character limit; the permission justifications are exactly the manifest's permissions; the only things saved are the port and the token, in local storage, never synced; no content scripts, no analytics or network path other than the loopback fetch); 9 mutants caught.
- Owed, and only a person can do them (HUMAN.md): a public address for the privacy policy; a 128 by 128 store icon and screenshots (the manifest declares no `icons`; the dashboard requires them); the publisher account with 2-Step Verification; entering the listing text in the dashboard. NOT VERIFIED: Chrome Web Store review itself, which no document can predict.

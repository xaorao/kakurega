# Cluster D: MCP and agent access

Scope: `crates/kk-cli/src/mcp.rs` (Kakurega commit `8eb997ce7c8a1cf890e7de51085bafdc54086eb1`), compared against the official Rust MCP SDK, the current MCP specification, six product codebases and other MCP servers. Read-only study; no existing file was changed.

Labels: VERIFIED (read in source or run), OBSERVED (seen in a document or tool output but not byte-checked, or not re-run), INFERRED, ASSUMED, UNKNOWN. Spec pages were fetched through a summarising fetch tool; their text looked near-verbatim but is OBSERVED, not VERIFIED, and every normative claim below should be re-read on the original page before it becomes a test.

## Verdict in six lines

1. Kakurega's server is a correct but thin 2025-06-18 stdio server. The current stable spec is 2026-07-28 (stateless, `server/discover`, `subscriptions/listen`, tasks extension, multi-round-trip requests). The audit is right that nothing in the SDK or spec was studied when it was written.
2. Reading the code found real defects, independent of any redesign (section 5): four of seven tools return fields their own `additionalProperties: false` output schema forbids; "cannot probe your file system" is false for `.json` and `.kkg` paths; the 1 MiB line cap is checked after the whole line is buffered; there are no request timeouts; an unknown tool is a tool result, not a protocol error.
3. "Cannot approve" holds only at the tool surface. With no approver key enrolled, the admin token alone approves (VERIFIED, `service.rs` `admin_approve`), and `kaku mcp` reads that token from `admin.json` in the data directory, which any same-user agent shell can read too.
4. Returning more than counts is safe only as a disclosure to a recipient that is not the approved recipient, so it must run through the same Cedar read check, disclosure ledger and signed log as every other release, with an owner grant signed by the approver key. Section 6 defines the tiers.
5. Recommendation: adopt `rmcp` (dependency, no copied files) as the protocol and transport layer, keep Kakurega's own validators, golden contract and process isolation. Measured cost is small (section 4).
6. Elicitation must never be an approval channel: Codex auto-accepts empty-schema confirm elicitations when its permission prompt is auto-approved (VERIFIED, section 3 row D29).

## 2. What Kakurega's MCP server is today (VERIFIED, `mcp.rs`)

- Hand-written JSON-RPC 2.0, one message per line over stdio, protocol constant `2025-06-18` (line 5). `initialize` ignores the client's requested version and capabilities and always answers 2025-06-18 (lines 254-256). No `server/discover`, `resources/*`, `prompts/*`, pagination, progress, cancellation, subscriptions, completion or logging. `notifications/*` are accepted and dropped (line 270).
- Seven tools, each with `inputSchema` (`additionalProperties: false`), `outputSchema`, `title`, annotations (lines 21-56). Success returns both a text block and `structuredContent` (lines 58-64). Errors return `isError: true` with a JSON text body and no `structuredContent`.
- Argument checking is hand-written and string-only (lines 70-123): unknown keys, missing required, length, control characters, one hard-coded id pattern. Other types return "unsupported type".
- `verify_capsule` and `verify_log` run in the MCP process on files ending `.kkg` or `.json`, regular files up to 20 MiB (lines 125-138). The other five tools call the service over loopback with the admin bearer token read from `admin.json` (`approve.rs` 12-33). The MCP process never holds vault keys. That isolation is worth keeping.
- Requests are handled one at a time in the reader loop (lines 279-297). The `ureq` agent has no timeouts configured (`approve.rs` 21-26).

## 4. SDK versus hand-written

Evidence (all VERIFIED unless marked):

- Fit. `rmcp` 3.8.0 is Apache-2.0 at crate level with MIT-licensed legacy contributions; depend on it, do not copy files, and list it in the third-party notices. MSRV 1.88, edition 2024; Kakurega's toolchain is 1.94.1 (`rust-toolchain.toml`) and edition 2021 crates may depend on edition 2024 crates. `worker-loop.md` line 13 records that a toolchain bump to 1.94.1 already happened for another reason.
- Dependency cost. A probe crate asking for `server, macros, transport-io` resolved 66 packages besides the probe itself; 61 are already in Kakurega's `Cargo.lock` at the same name and version (tokio 1.54.1, serde, serde_json, schemars 1.2.3, sha2 0.11.1, tokio-util, chrono, uuid, indexmap, futures, tracing, thiserror 2). Caveat: the probe resolved with its own fresh lockfile from the offline cache; Kakurega's lock could pick different versions.
- Runtime fit. `kk-cli` already links `kk-service` and `kk-companion`, which use tokio (`rt-multi-thread`) and axum 0.8. `kaku mcp` is currently synchronous (`ureq`). Migrating means building a runtime in that subcommand and either keeping `ureq` inside `spawn_blocking` or moving the admin client to an async client. rmcp's stdio transport needs tokio features `io-std` and `net`.
- Size. The probe (one tool, release profile, no LTO) is 3.4 MB unstripped, 2.8 MB stripped. Kakurega's `kaku` binary size and the true increment are UNKNOWN (not built here); expect a smaller increment than the probe because tokio, serde and schemars are already linked.
- What it replaces. Framing with a line cap, JSON-RPC dispatch, version negotiation for 2024-11-05 to 2026-07-28, per-request tasks and cancellation tokens, `server/discover`, cache hints, subscriptions, task capability gating, HTTP transport with Host and Origin checks, request-state HMAC codec, tool-name validation, schema generation. - What it does not replace. Input constraints (no JSON Schema validator in its dependencies), per-principal task binding and durability (TaskManager is in memory and unbound), rate limits (no semaphore found), Origin enforcement by default (empty allowlist means off), the golden contract, uniform file errors, canary scanning.

Oversize lines are dropped without an error reply (probe); replies are unordered, so the existing tests that index responses by position must correlate by id; `ServerHandler` defaults answer `initialize` for any listed legacy version unless `supported_protocol_versions` is overridden.
- Churn risk. Codex pins `rmcp = 3.5.1` by git revision (VERIFIED, `codex-rs/Cargo.toml` line 471); goose uses `3.4.1` (VERIFIED, `Cargo.toml` line 21); the SDK describes a 2.x to 3.x migration guide (OBSERVED, `README.md`). Pin an exact version and budget an upgrade review each minor.

IMPROVE on top with the validators, scoped token, tier checks and signed-log entries. Do not use its `TaskManager`. Do not copy any SDK source file. ## 5. Defects found in the current server (fix independently of the migration)

1. Output schemas contradict responses (D17). Four tools return keys their `additionalProperties: false` schema forbids. Not run against a strict validating client; found by reading `mcp.rs` 40-54 against `service.rs` 2333-2389 and `verify.rs` 85-96.
2. File probing claim is false. `docs/mcp.md` line 29 says the tool cannot be used to probe the file system. `read_small` returns "cannot read that file" for a missing or wrong-extension path but a normal `valid: false` answer for an existing readable `.json` or `.kkg` file up to 20 MiB, so existence and rough size of any such file are observable (VERIFIED by reading; the repo's own test mc03 asserts both outcomes).
3. Line cap after buffering (D06).
4. No timeout on loopback calls (D07).
5. Unknown tool is not a protocol error (D05).
6. Approval claim needs a precondition (D32, 6.4): with no approver enrolled, the admin token approves.
7. No audit trail of agent calls (D35).
8. The `recipient` string is chosen by the agent and shown to the owner in the approval; the enclave helper accepts only printable ASCII (VERIFIED, `approval-binding.md`) but the MCP path allows any 1-128 non-control characters, so a lookalike recipient can reach the approval screen (INFERRED; confirm what the terminal and desktop dialogs render).

## 6. How Kakurega can expose more without leaking or bypassing approvals

### 6.1 Principle

An MCP client is a sink: whatever it receives goes to the agent's model provider, a route Kakurega cannot attest. A release approval names one recipient and one digest (`approval-binding.md`); an agent that started the review is not thereby that recipient, so approved release bytes must not also be returned to the agent. Anything beyond counts is therefore a new disclosure and must pass the same checks as the other disclosures, using the machinery that already exists:

- the Cedar policy in `kk-policy` (one engine): add a principal kind `MCP_CLIENT` to the `Worker` entity, a `Route` of class `agent_host` with `tee_verified: false`, and an action `read.artifact` for that principal with clearance taken from the owner's grant (default `Public`, no compartments). The existing forbid rules for tainted data on unverified routes then apply with no new policy language (INFERRED from `schema.cedarschema` and `default.cedar`; whether the kernel computes taint for derived finding text was not read).
- the disclosure ledger in `kk-disclosure` (it already has `escalate_coverage`, `block_coverage`, `max_releases_per_day`, `min_project_files`, VERIFIED first 30 lines) so repeated small reads cannot add up to a whole project.
- the signed event log, with `mcp.read` entries (D35).

### 6.4 Keeping approvals human-only (enforceable, not cosmetic)

1. Today the guarantee is only the tool list. `admin_approve` skips the proof check when no approver is enrolled (VERIFIED, `service.rs` 2245-2270), and the MCP process holds the same token that a same-user shell can read from `admin.json`. Fix: `request_approval` and `start_review` refuse to run, with a clear message, when the service reports `requires_proof: false`; the observer profile still works.
2. Scoped agent token (needs Prateek's decision). Extend the companion guard (`app.rs` 142-170, `admin_matches`) so that tokens carry a scope; an `agent` scope reaches only an allowlist of routes (overview, jobs read and create, approval request, read-only tier routes) and never `/admin/approvals/*/approve|deny`, `/admin/approvers*`, `/admin/pairing`, `/admin/extension*`. It is the same bearer check with a scope table, not a second permission system. Honest limit: an agent with shell access as the same user can still read the raw admin token; against that only an enrolled approver key, ideally Secure Enclave with presence, protects approval.
3. Origin attribution: the approval record, the approval window and the log entry say "requested through MCP token T" using the service-side token identity, never the client-supplied `clientInfo`.
4. Pending-approval cap per token (D33) to avoid approval fatigue.
5. Elicitation never counts as consent (D29).

OpenClaw's bridge exposes `permissions_respond` with `allow-always` to the same MCP caller that can start work, with no tool annotations (VERIFIED, `channel-server.ts` 240-257 and a grep). That is the pattern Kakurega must keep refusing; its absence is a feature to keep in the contract test (the existing `mc02` forbidden-name check already covers it).

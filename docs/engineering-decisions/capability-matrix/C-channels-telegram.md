# Cluster C: Channels (Telegram first)

Scope: Kakurega's Telegram bridge (`crates/kk-cli/src/telegram.rs`, 638 lines including 6 tests) measured against the channel layers of OpenClaw, Hermes Agent, Goose, IronClaw, Ghast companion_service, Privateer, AnythingLLM and Cline.

Labels: VERIFIED = I read the code or doc lines cited, or ran nothing but read exactly what is cited; OBSERVED = seen in a listing, grep hit or search snippet only; INFERRED = reasoned; ASSUMED; UNKNOWN. Nothing in this file was executed. No Kakurega file was modified.

Binding rule used throughout: a chat service is an untrusted transport. Consequential approvals stay on a trusted surface. Messages carry counts and ids only unless the owner opts in. One kernel, one approval path: nothing below proposes a second policy engine, secret store or release path.

## 2. Findings in Kakurega's own bridge (VERIFIED by reading `telegram.rs`)

These come first because they change the priorities below. Line numbers refer to `telegram.rs`.

| # | Finding | Evidence | Severity |
|---|---|---|---|
| K1 | **Failed sends are silently treated as success.** The agent is built with `http_status_as_error(false)` (263-267), and ureq 3.5.1 returns `Ok` for any 4xx/5xx in that mode. `send()` only reports `Err` (328-336), so a 429 flood wait, a 403 "bot was blocked by the user", a 400 or a 5xx produce no log and no retry. | ureq `Config::http_status_as_error` doc ("Defaults to `true`"); `send` code | High: a lost "approval waiting" notification is the product's core promise. The real-phone pass only exercised the success path |
| K2 | **Notification is marked seen before it is delivered.** `poll_notifications` writes `seen_states`/`seen_approvals` (158, 170) and the caller sends afterwards (316-318). With K1, one failed send loses that event forever, and nothing is persisted across a restart (`primed` false on start, 159 and 171). Events that happen while the bridge is down are never announced. | 144-177, 281-320, test tg03 asserts "does not replay old news" | High |
| K3 | **Revocation does not reach a running bridge.** `kaku telegram pair` deletes `telegram.json` and writes a new code (246-247), but the running process keeps `bound_chat = Some(old)` in memory; while bound, `/pair` is ignored (112-113 ignore other chats; 114+ only command branch), and `reload_code` only feeds a code that can never be used. The old phone keeps getting notifications until the bridge is restarted. | 89-113, 230-250, 269-285 | High for a lost-phone case |
| K4 | **No update-id durability.** `offset` starts at 0 each run (282). Telegram re-delivers unconfirmed updates, so a restart can replay the last batch (idempotent here: commands are read-only, a spent `/pair` code fails). | 282-300 | Low |
| K5 | **Polling is not long polling and has no failure ladder.** `getUpdates?timeout=2` (286), fixed 3 s sleep on error (304, 311), no 409 handling, no `deleteWebhook`. A bot that has a webhook set, or a second poller, gets 409 forever and the bridge only prints "telegram answered 409". No 401 distinction (a revoked token looks like a flaky network). No 429 `retry_after`. | 286-313 | Medium |
| K6 | **Pairing attempts are global, not per chat.** Five wrong tries from anyone close the window (103-107). A stranger who knows the bot username can burn the window (denial of pairing, not a bypass). Code is 32 bits of hex (243-245), stored in plain text in `telegram.pairing` with default permissions (247; mode UNKNOWN, `serve.rs` uses 0600 for admin.json but this file does not), compared with `==` (97). By contrast the browser pairing in `kk-companion/src/security.rs` 66-91 stores only a hash, uses a 128-bit token, and has a lockout window. Two different pairing implementations for one product. | 97, 103-107, 243-247; security.rs 66-91 | Medium |
| K7 | **Token scrub is string replacement at two call sites** (180-186, 307-310, 334). It covers exact token text only; any new error path that prints a URL or debug struct leaks. UNKNOWN whether ureq errors can print the token in a form the replace misses (percent-encoding of `:`). | 180-186 | Medium |
| K8 | **No health channel.** The bridge prints one line at start. Nothing tells the service, the web UI or `/status` whether the bridge is alive, when it last polled or sent, or that the token was rejected. | 281 | Medium |
| K9 | **Docs disagree.** `docs/LIMITS.md` line 10 says real Telegram delivery was not verified; the task statement says a real phone test passed. One of them is stale. | LIMITS.md:10 | Low, but the "say what is NOT covered" rule applies |
| K10 | **`seen_states` grows without bound**, and `/reviews` shows the first 15 jobs in service order (125), whose ordering is UNKNOWN. | 47, 125 | Low |
| K11 | Strengths worth keeping (VERIFIED): silence to non-bound and non-private chats and no request to the service for strangers (84-112, test tg01); fixed templates, ids reduced to `[A-Za-z0-9_-]{1,40}` (27-32, test tg03 with ESC and `<b>`); bot never echoes input (tg02 hostile list); `allowed_updates=["message"]` so callbacks, edits and group events are never delivered (286); read-only `Admin` trait (9-11); replies cut to 1500 chars (136); token from env or file, path never echoed (188-205, tg04). | as cited | n/a |

## 4. What the references get wrong or do worse than Kakurega (honest comparison)

VERIFIED from the cited lines unless marked.

- Every chat-approval implementation (OpenClaw, Hermes, Goose, Privateer, AnythingLLM) sends the action description into the chat and accepts "allow always" from the chat. OpenClaw's own doc says channel delivery shows the command text (`rich-messages.md` 188) and recommends enabling group delivery only in trusted groups.
- Cline's Telegram connector is open to anyone who finds the bot unless the user passes `--allowed-user-id` (`connectors.mdx` 57-77).
- AnythingLLM uses a six-digit code held in memory, with a cap on pending requests but no attempt limit visible in the lines read (`verification.js` 12-38).
- Goose uses a six-character code (about 30 bits) and no attempt limit in the lines read (`pairing.rs` 267-275, `handler.rs` 139-185); it replies "Welcome! Enter your pairing code" to unknown users.
- Hermes approval ids are a process-local counter (`adapter.py` 4256-4262): guessable, and lost on restart.
- OpenClaw hands a bootstrap token with `operator.admin` to the chat for mobile pairing (single-use, 10 minutes, `pairing.md` 204-222). That is acceptable for them and wrong for us.
- Ghast documents compromised messaging platforms as out of scope (`security/overview.md` 43). Kakurega's counts-only rule is a stronger stance, but counts and timing are still metadata (see 6, U4).

## 6. Prioritised implementation order (top 10) for the Rust bridge

Each item names what to adapt and from where. Licences: IronClaw MIT OR Apache-2.0 and Goose Apache-2.0 allow adapting Rust code with NOTICE entries; OpenClaw and Hermes (MIT) are TypeScript/Python, so rebuild from the behaviour described above and credit the design in NOTICE.

1. **Typed send outcome and real status handling (fixes K1).** One `call(method, body) -> Outcome` with `Sent | Retryable{retry_after} | Unauthorized | Permanent | Ambiguous`; map statuses as IronClaw `channel.rs` 593-598 and the transport-error rule from OpenClaw `network-errors.ts` 58-73 (retry only proven pre-connect failures; ambiguous sends are marked, not blindly resent). The error type never carries the URL (Goose `without_url` idea, `telegram.rs` 728-740). Tests: fake Bot API with 429/403/500/reset.
2. **Durable outbox with announce-once identity (fixes K2).** Hermes `delivery_ledger.py` states and crash semantics rebuilt in Rust; event id from job id + state (+ approval id); replay-on-start only for items still pending, as one digest; dead-chat flag on 403 (`dead_targets.py`). 
3. **Live revocation, unpair, multi-chat-ready binding file (fixes K3).** Bridge re-reads binding every cycle; `kaku telegram unpair [chat]`; in-chat `/unpair`; store `chat_id` and `from.id`; drop `from.is_bot`.
4. **One pairing primitive (fixes K6).** Reuse `kk-companion::Security` hashing, TTL and lockout; per-chat attempt budget plus global lockout, persisted; unambiguous display alphabet and whitespace tolerance (Hermes `pairing.py` 461, 500-530); deep link and QR from `getMe` (IronClaw README/telegram.mdx line 94); log the binding in the evidence event log so pairing is auditable by the kernel.
5. **Polling lifecycle (fixes K5).** `timeout=25`; `deleteWebhook` at start and on 409; exponential backoff 2 s to 60 s with jitter and reset (OpenClaw `polling-session-restart-policy.ts` 3-53 shape, shorter constants); 401 = blocked and stop; stall detection at 3 minutes (OpenClaw `polling-session.ts` 485-499).
6. **Health file, `/status` footer, `kaku telegram doctor` (fixes K8).** Privateer heartbeat shape (30 s); OpenClaw tokenFile-is-regular-file check; mode 0600 checks; reconcile `LIMITS.md` line 10 with the real-phone test evidence (K9).
7. **Flood gate and pacing.** OpenClaw `TelegramFloodGate` (`account-throttler.ts` 112-128) deadline model; Hermes rule never to sleep a long `retry_after` inline (`adapter.py` 3560-3590); 1 msg/s per chat, digest above 5 events/10 s; `/mute`.
8. **Approval-ping lifecycle.** Remember the message id of "approval waiting" and edit it to "resolved on your computer" or "expired" (OpenClaw `callback-router-controls.ts` 105-146 terminalisation idea; no inbound power added). Add review id and exact local command to the text.
9. **Update receipts and test harness.** Hermes `update_admission.py` receipt set (24 h TTL, bounded) rather than a watermark; Rust fake Bot API with inject/drain/fail hooks after IronClaw `telegram_mock.py`; implement the catalogue in section 5; token-sweep test across all error kinds (Hermes `test_telegram_error_redaction.py`, Goose tests 1218-1325).
10. **Transport trait and a second, more private doorbell.** Extract the outbox + outcome + pairing into a `Transport` trait; implement ntfy (one-way, self-hosted) and one end-to-end encrypted option (Signal or Matrix) after verifying their protocol docs. Optional signed "mute / unpair" buttons only after items 1-9 and only with callbacks that cannot reach an admin write.

Explicitly not on the list: approving through any chat, chat-as-agent, groups, media, markdown/HTML, personal-account (MTProto) access, stranger-first pairing, bootstrap tokens through chat.

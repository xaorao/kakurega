# Proposed fixes: several changes in one file (ledger E-C1)

## Target experience
- A real fix often touches more than one place of a file. The model can say so in one fix, the owner sees one diff with only the lines that change, applies it with one confirmation and undoes it with one click.
- Nothing about "exactly the text the owner saw" gets weaker: every change is found once in the file as it is, and nothing is guessed.

## Sources read
- OpenClaw `src/agents/apply-patch-parse.ts` and `apply-patch-update.ts` (MIT, commit f38495f7d, a port of the Codex `apply_patch` grammar): READ IN FULL (218 and 325 lines). Taken: several chunks per file are located against the original, in file order, and joined into replacements applied together; CRLF and a byte order mark are kept. Not adopted: tolerant matching of whitespace, dashes and quotes (it accepts text that is not really there), the `@@` context anchors and order dependence (ours is exact and order free), Add/Delete/Move operations (a fix here changes existing text only).
- Codex `apply_patch` itself: the local clone does not contain it (checked: no `apply-patch` crate, no `*** Begin Patch` anywhere); the grammar was known from the OpenClaw port. NOT READ: Codex's own `parser.rs` and `lib.rs`, OpenCode `edit.ts` (read in an earlier row), Cline `apply-patch.ts`.
- Found in our own code while reading: `apply_fix` counted only non-overlapping matches, so `aa` in `aaa` passed as "exactly once". Fixed and tested.

## Behaviour
- A fix is at most 8 changes in at most 4 files; several may be in one file (`also` may repeat a file). Each `old_text` and `new_text` is at most 8,000 characters, as before.
- `consolidate` joins the changes of one file into one change of the span they cover, before anything is checked: each `old_text` must be in the file exactly once as it is now (overlapping matches count), no two may share a byte (touching is fine), the order written does not matter, the file must be text, and the span from the first to the last change is at most 200,000 bytes. The joined change is the text a person would get by making the changes one by one (property test, 300 random sets). A set that cannot be joined or made is not offered.
- Everything after that still handles exactly one change per file: the checksum of the reviewed file, the saved original, applying, undoing (the text the fix wrote must still be there exactly once), crash recovery. `apply_all` now refuses a fix that names a file twice, instead of letting the second change overwrite the first.
- The diff is a real line diff of before and after with three lines of context; lines that are the same on both sides are context, and changes more than six unchanged lines apart are separate hunks. A rewrite too large to compare (over 4 million line pairs) is shown as one replacement. For every random set of changes the diff, applied to the file, gives the changed file (test f23).

## Evidence
- kk-review f20–f29 (joining, refusals, one-byte overlap, order, touching, bounds, 300-round diff round trip, hunk separation distance, huge rewrite, duplicate file), job j11 in the Linux sandbox (a model proposes a two-change fix: it is joined, checked against the reproducer and the project's own tests, shown as one diff; a fix with a missing or overlapping change is not offered), browser e2e 233/233 (the UI shows both changes, applies both, undoes to the exact original bytes). 22 mutants of check.rs and job.rs: all caught after four tests were added for survivors (one equivalent mutant).
- Weakness kept on purpose: undo of a joined change needs the whole joined text to still be there, so an edit made by hand between two changed lines blocks undo of that fix (it says so and restores nothing) instead of guessing; per-change undo would keep such edits.

## Not covered
- Hunks in a file larger than the span bound, files that are not UTF-8, deleting or creating files, renaming. The model's choice of hunks is not judged, only that they apply exactly.

## Error text that could quote source (ledger E-C9)
- Reference: OpenCode `packages/core/src/tool/plugin/edit.ts` (fe04656, MIT), lines 290-345 of 368 read by me (the not-found, many-matches and no-change failures): a "miss hint" that shows file contents is produced only when reading that file is already permitted, and the other failure messages quote the path and counts, never file text.
- Audit of ours (VERIFIED by reading and by a scan): the only message that carries anything derived from program output is `missing_package` (check.rs), which accepts a Python module or an npm package name only after a character-by-character test and repeats only the top segment (test c23). The edit and fix failures (`CouldNotApply` and the test-run summaries) are fixed words and counts. No `format!`, `write!`, `println!`, `panic!` or `anyhow!` in `kk-review`, `kk-worker`, `kk-sandbox`, `kk-run` or `kk-kernel` interpolates a variable named stdout, stderr, output, content, text, source, body, snippet or diff.
- Guard added: `scripts/check_error_text.py` (with a self-test that finds four planted violations and passes four clean lines) runs in `scripts/test` and fails if such an interpolation ever appears, unless it is named in ALLOWED with a reason. It is a name-based scan, so a variable with another name would pass; the label check on what a viewer may see stays the real control.
- Not covered: messages in `kk-service` and the web page that show findings or reproducer output to the owner (these are shown to the owner, who may see their own files; the release path to a recipient is governed by the disclosure pipeline, not by this scan).

## Making a change fit its file (ledger E-C2)
- Reference: OpenCode `packages/core/src/tool/plugin/edit.ts` (fe04656, MIT), lines 1-345 of 368 read by me. It matches exact text first; failing that, a reading that treats look-alike quotes, dashes and spaces as the plain ones (one character for one character, so offsets still map back); failing that, a line-by-line reading that ignores spaces at the ends of lines; it reads through the LF view of a CRLF file and writes the replacement with the endings of the region it replaces, and it reuses the file's own line for any replacement line that is unchanged (longest common subsequence). Its replace-all and "closest lines" hint are not taken (our fixes name one exact span per file; the hint would quote source, see E-C9).
- Taken, with the matrix's condition: a looser reading is used only when it finds exactly one place. Ours (`kk-review/src/align.rs`): the exact text always wins and is left alone, even when a looser reading would find it elsewhere too; an ambiguous exact text is never rescued; only when the exact text is nowhere is a looser one tried, first the character reading (look-alikes, CRLF), then the line reading (ends of lines ignored); two or more places, or none, means no change is made and the fix is refused as before. What is applied, shown in the diff and run against the reproducer is the file's own text at that place (`align_fix` runs before the consolidation step), the model's copy is never used for the span, lines the change leaves alone keep the file's bytes (including trailing spaces and curly quotes), and new lines take the file's line endings (CRLF in a CRLF file, none written into a file without them).
- Differs from the reference on purpose: no replace-all, no hint, indentation and zero-width or direction characters are never look-alikes (a different depth or an invisible character is a different text), and an empty or all-blank wanted text finds nothing.
- Evidence: kk-review al01–al08 (exact wins; quotes, dashes and spaces; multi-byte text; CRLF both ways and mid-line starts; trailing spaces with unchanged lines keeping their bytes; two places, none and indentation refused; hostile zero-width, direction and bare-CR texts; twenty thousand candidate places answer without a match) and fa01 through the real apply and diff (the file's text is what is applied and shown). 11 mutants caught after two assertions were added.
- Not covered: tabs against spaces (not a look-alike here), a fix that spans a file whose bytes are not UTF-8 (left to be refused), a real model's rate of such near misses (NOT VERIFIED how often this rescues a fix), the end-to-end review test with a model that writes curly quotes.

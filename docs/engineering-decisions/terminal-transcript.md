# Terminal transcript: search, copy, export (ledger A-A31)

## Target experience
- A long conversation in the terminal can be searched for a word, its last answer (or all of it) put on the clipboard on request, and the whole of it written to a file the owner names, without leaving the workspace.

## Sources
- Codex `pager_overlay.rs`, `/copy`, `/export` markdown, `/raw`; OpenCode message actions (copy, fork); Hermes `/copy`, `/save`, OSC 52 (`lib/osc52.ts`); Cline `session/export.ts`; Goose `session export`: all as recorded in the matrix (listings and summaries). NOT READ in source for this row. Decision follows the matrix: an explicit user request for any copy, the clipboard warning in the confirm text, export through the service to one place, not a terminal-specific path.

## Behaviour
- `/transcript WORDS` lists up to 30 lines of the conversation that hold every word (any case), with each word's first place marked `[[like this]]` so it shows without colour, and says how many lines matched. Search results are not themselves part of the conversation.
- `/copy` asks ("Copy N characters to the system clipboard? Other programs can read the clipboard. [y/N]"), and only a `y` hands the last reply (or `/copy all`, the whole conversation) to the screen loop, which writes one standard OSC 52 sequence (`ESC ] 52 ; c ; base64 BEL`). Base64 has no escape or bell, so text cannot end the sequence or start another. Nothing over 74,000 bytes is copied; the message points to `/export`. Nothing is ever copied automatically.
- `/export NAME` sends the conversation text (what the owner typed after "You:", each message under its title; commands and search results left out) to `POST /api/exports/transcript`, which writes a new file `NAME.md` (or `.txt`) with mode 0600 in `<data folder>/exports`. A name is 1 to 60 letters, digits, dots, dashes or underscores, not starting with a dot. An existing file is never replaced (409). Text over 512 KiB (under the 1 MiB every request may be), empty, with hidden or direction characters, or that looks like a secret is refused and nothing is written. The signed log records that an export happened and its length, not the name or words.
- Evidence: kk-service sv91 (path inside exports, 0600, 409, 11 bad names, 5 refused texts, log), kk-tui tu45 (base64 vectors, a sequence that decodes to exactly the chosen bytes, hostile text cannot end it, size limit) and tu46 (2000-line search with markers and the 30 limit, case, copy asks and only y copies exactly the last reply, copy all, export request and its answers), PTY 34/34 (a real terminal receives the sequence only after `y`; the exported file holds both sides and no commands). 21 mutants caught after two assertions were added.
- Not covered: whether a given terminal accepts OSC 52 (many disable it; nothing is shown to the owner then, and the message says "Copied." because the program cannot tell), selecting a region by keyboard to copy, a full-screen overlay (this is commands, not an overlay), exporting a kept web conversation.

## Branch a kept conversation in the terminal (ledger A-A04)
- Reference: OpenCode `fork.ts` (fork a session before a prompt), as recorded for the web in `web-shell.md` (B-W15); the terminal row names OpenCode's session fork and Codex's side conversations, whose sources were not re-read for this row (NOT READ). The behaviour is the service's branch route: a branch is a new kept conversation holding the first N messages, the original is never changed.
- Behaviour: `/branch` copies the open kept conversation whole, `/branch N` cuts it after message N (0 starts empty); the copy is opened at once and new messages go to it; the original stays in `/sessions`. An unkept conversation says to `/keep` first; a number beyond the conversation, words, a negative or a huge number are refused by the command without asking the service; a refusal from the service (for example too many conversations) is shown and nothing is opened.
- Evidence: kk-tui tu49 (every case above, the request path and body, the copy being opened); 5 mutants, 4 caught and one equivalent (a failed answer has no id, so it cannot open). 
- Not covered: a switcher between versions in the terminal (the web has one), picking a message to branch at from a list, the PTY end-to-end for this command.

## Resume at launch (ledger A-A03)
- Reference: OpenCode's `--continue` and Codex's resume picker (as recorded in matrix A); their sources were not re-read for this row (NOT READ). The behaviour is ours on the existing kept-conversation store.
- Behaviour: `kaku --resume` (or `kaku tui --resume`) opens the terminal workspace and then the newest kept conversation (the service lists newest first), with its messages on the screen and new messages saved to it; with none kept it says so in one sentence; a refusal from the service is shown. The flag is never passed to the service it starts.
- Evidence: kk-tui tu50 (newest opened, none kept, service refusal, a malformed entry opens nothing); the real-terminal test (38/38): a conversation is kept and a message sent, the workspace is closed, `kaku tui --resume` on the same data shows that message and says it was opened from the store, and exits cleanly. Mutants: never opens and opens-the-oldest caught; opens-on-failure is equivalent (a failure has no list). A finding on the way: the pty test must keep reading the screen while it waits for exit, because the screen redraws constantly and an unread pipe blocks the program.
- Not covered: `--resume ID` for a chosen conversation, resuming a review, a picker at launch.

## Bell and window title (ledger A-A11)
- References as read for matrix A11 (Codex `notifications/mod.rs` 1-40, OpenCode `attention.ts` 1-80, Goose `program_status.rs` 1-50; depths in the matrix). Not read: the exact Goose escape sequence, so none of it is copied.
- Built (`kk-tui/src/attention.rs`, wired in `app.rs` and `run.rs`): when a review finishes (ready) or stops (failed, nothing to release) the terminal rings the bell once and the window title becomes `Kakurega: a review is ready` or `Kakurega: a review stopped`; the title returns to `Kakurega` when the terminal regains focus or the owner presses a key. The phrases are constants: no recipient, folder, job id, file or finding can reach the bell or title (they are shown by the terminal's tab bar, tmux, screen shares and the desktop's history). `KAKU_NOTIFY=off` (also `0`, `false`, `no`) turns both off. Focus reporting (`?1004`) is requested and released on exit; a terminal that never reports focus leaves it unknown and the bell rings, because it is harmless and the only signal that terminal can carry.
- Differs from the matrix decision: the matrix named three events including "approval waiting"; the terminal only opens an approval when the owner types `/approve`, so "a review is ready to approve" is the event that exists. OSC 9/777 desktop notifications are not sent: no terminal detection was verified, so BEL only. Service errors are not announced yet.
- Evidence: kk-tui at01–at03 and tu51 (events, one-shot, clearing, no job data), `tests/e2e/tui_pty.py` on the real binary in a real terminal: exactly one bare bell after a finished review, title text without the folder, recipient or job id, focus reporting asked for and released. 8 mutants caught.
- Not covered: how real terminals render the bell (some are silent by setting), tmux pass-through, OSC 9/777, a service-error notice, restoring the user's old title on exit (the title stays `Kakurega`).

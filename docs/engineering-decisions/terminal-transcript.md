# Terminal transcript: search, copy, export (ledger A-A31)

## Target experience
- A long conversation in the terminal can be searched for a word, its last answer (or all of it) put on the clipboard on request, and the whole of it written to a file the owner names, without leaving the workspace.

## Sources
- Codex `pager_overlay.rs`, `/copy`, `/export` markdown, `/raw`; OpenCode message actions (copy, fork); Hermes `/copy`, `/save`, OSC 52 (`lib/osc52.ts`); Cline `session/export.ts`; Goose `session export`: all as recorded in the matrix (listings and summaries). NOT READ in source for this row. Decision follows the matrix: an explicit user request for any copy, the clipboard warning in the confirm text, export through the service to one place, not a terminal-specific path.

## Behaviour
- `/transcript WORDS` lists up to 30 lines of the conversation that hold every word (any case), with each word's first place marked `[[like this]]` so it shows without colour, and says how many lines matched. Search results are not themselves part of the conversation.
- `/copy` asks ("Copy N characters to the system clipboard? Other programs can read the clipboard. [y/N]"), and only a `y` hands the last reply (or `/copy all`, the whole conversation) to the screen loop, which writes one standard OSC 52 sequence (`ESC ] 52 ; c ; base64 BEL`). Base64 has no escape or bell, so text cannot end the sequence or start another. Nothing over 74,000 bytes is copied; the message points to `/export`. Nothing is ever copied automatically.
- `/export NAME` sends the conversation text (what the owner typed after "You:", each message under its title; commands and search results left out) to `POST /api/exports/transcript`, which writes a new file `NAME.md` (or `.txt`) with mode 0600 in `<data folder>/exports`. A name is 1 to 60 letters, digits, dots, dashes or underscores, not starting with a dot. An existing file is never replaced (409). Text over 512 KiB (under the 1 MiB every request may be), empty, with hidden or direction characters, or that looks like a secret is refused and nothing is written. The signed log records that an export happened and its length, not the name or words.
- Evidence: kk-service sv91 (path inside exports, 0600, 409, 11 bad names, 5 refused texts, log), kk-tui tu45 (base64 vectors, a sequence that decodes to exactly the chosen bytes, hostile text cannot end it, size limit) and tu46 (2000-line search with markers and the 30 limit, case, copy asks and only y copies exactly the last reply, copy all, export request and its answers), PTY 34/34 (a real terminal receives the sequence only after `y`; the exported file holds both sides and no commands). 21 mutants caught after two assertions were added.
- Not covered: whether a given terminal accepts OSC 52 (many disable it; nothing is shown to the owner then, and the message says "Copied." because the program cannot tell), selecting a region by keyboard to copy, a full-screen overlay (this is commands, not an overlay), exporting a kept web conversation.

## Bell and window title (ledger A-A11)
- References as read for matrix A11 (Codex `notifications/mod.rs` 1-40, OpenCode `attention.ts` 1-80, Goose `program_status.rs` 1-50; depths in the matrix). Not read: the exact Goose escape sequence, so none of it is copied.
- Built (`kk-tui/src/attention.rs`, wired in `app.rs` and `run.rs`): when a review finishes (ready) or stops (failed, nothing to release) the terminal rings the bell once and the window title becomes `Kakurega: a review is ready` or `Kakurega: a review stopped`; the title returns to `Kakurega` when the terminal regains focus or the owner presses a key. The phrases are constants: no recipient, folder, job id, file or finding can reach the bell or title (they are shown by the terminal's tab bar, tmux, screen shares and the desktop's history). `KAKU_NOTIFY=off` (also `0`, `false`, `no`) turns both off. Focus reporting (`?1004`) is requested and released on exit; a terminal that never reports focus leaves it unknown and the bell rings, because it is harmless and the only signal that terminal can carry.
- Differs from the matrix decision: the matrix named three events including "approval waiting"; the terminal only opens an approval when the owner types `/approve`, so "a review is ready to approve" is the event that exists. OSC 9/777 desktop notifications are not sent: no terminal detection was verified, so BEL only. Service errors are not announced yet.
- Evidence: kk-tui at01–at03 and tu51 (events, one-shot, clearing, no job data), `tests/e2e/tui_pty.py` on the real binary in a real terminal: exactly one bare bell after a finished review, title text without the folder, recipient or job id, focus reporting asked for and released. 8 mutants caught.
- Not covered: how real terminals render the bell (some are silent by setting), tmux pass-through, OSC 9/777, a service-error notice, restoring the user's old title on exit (the title stays `Kakurega`).

## Plain-line mode for screen readers and pipes (ledger A-A35)
- References (matrix A35): Codex `screen_reader.rs` 1-90 (detects a screen reader once and turns animation off; the detection function, lines 90-193, NOT READ, so detection is not copied: the mode is chosen by the owner); OpenCode's semantic dialog labels (`permission.tsx`, listed). The design is ours.
- Built (`kk-tui/src/linear.rs`, `kaku tui --linear` or `KAKU_LINEAR=1`): the same `App`, commands, approval and service, with plain lines in and out. No alternate screen, no raw mode, no cursor addressing, no colour: the e2e test asserts not one control byte is written. Each card is written once, whole, starting with its kind in words (`[Done]`, `[Warning]`, `[Error]`, `[Note]`, `[Notice]`); a streaming answer is announced once and written when finished (a half-written answer is never read out); the status line is written when it changes; a finished review is a `[Notice]` line (no bell). Overlays become prompts that say what to type: the approval prints the whole release once, names the 12-character prefix to type and says `refuse` refuses; a wrong prefix writes only the error line, not the release again; a yes/no question accepts `y` or `yes` and treats anything else as no; a list is numbered and takes a number, words to narrow it, or `cancel`. The owner's own typed lines are written back only when stdin is not a terminal (a terminal already shows them). Copy and the external editor say they are not available in this mode instead of silently doing nothing.
- Differs from the matrix wording: the matrix allowed cursor addressing in the approval prompt; there is none anywhere. No detection of a screen reader.
- Evidence: kk-tui tu56–tu61 (cards, once-only output, streaming, yes/no, approval, list) with 11 mutants (10 caught; the 11th was a reset made redundant by the next line, removed); `tests/e2e/tui_linear.py` drives the real binary through pipes (21 checks: review, wrong then right approval prefix, delivery, refused approval on a second review, chat, numbered list, yes/no, clean exit, no control byte).
- NOT VERIFIED: use with a real screen reader. VoiceOver on this Mac was not run; it is a person's check (HUMAN.md). Not covered: mouse, `/transcript` scrolling (not needed here), width wrapping (lines are left to the reader to wrap), long-running answers with no output (only the one announcement), Windows consoles.

## Formatted answers in the terminal (ledger A-A29)
- Reference read by me: Codex `tui/src/markdown_render.rs` (commit 021fccb, Apache-2.0), lines 1-60, 105-215 and 368-470 of 3,267: it renders `pulldown-cmark` events into styled lines with theme colours, task lists, table layout with column-width allocation and a key/value fallback, wrapping, local file link display and hyperlink metadata. NOT READ: its writer (lines 467-2593), tables, math, Mermaid and the other render files. Hermes' and OpenCode's renderers were not read.
- Decision: BUILD our own, not `pulldown-cmark`. Reason: the web page already has a deliberately small, safe reader (`markdown.ts`), and a terminal that understands a different grammar would show the same answer differently on two surfaces. So `kk-tui/src/markdown.rs` is a port of that reader (same block and inline rules), and one shared set of 42 cases (`tests/fixtures/markdown_cases.json`, generated from the web reader) is checked against both: the terminal test fails if the two trees ever differ (only the form of a link's address differs: the browser writes `https://example.com/`, the terminal shows what the model wrote).
- Built: answers (cards titled Assistant and Aside) are shown with headings in bold, bold and italic, inline code in yellow (reverse video without colour), bullets and numbers with a hanging indent, quotes with a bar, fenced code in its own colour with its spaces and tabs kept and a line that is too wide cut rather than reflowed, wrapping by words with styles kept and wide characters whole. Links are never clickable and never hide where they go: `docs (https://example.com/guide)`; an unsafe link (not https, with credentials, spaces or markup characters) is plain words with the address visible; an image is `[image: description]` and nothing is fetched. What copy, export, search and plain-line mode see is the text as the model wrote it. What the answer cost and used is its own plain card after the answer now (so only the answer is formatted).
- Found by testing it hostile: rendering once rescanned the whole answer for every block (an answer of 10,000 code fences took 37 s); fixed. A bracket with no end in sight rescanned the rest of the line from every bracket (200,000 brackets took 31 s); each label and address is now looked for within 2,200 characters (0.7 s).
- Evidence: kk-tui md01 (42 shared cases against the web reader), md02-md07 (links, shapes and widths of every block, no word lost or width exceeded for narrow screens and wide characters, hostile input finishes, code kept as written), tu66 (the screen shows no `**` or fences, the words between stars are bold with and without colour, export and plain-line mode keep the model's text, other cards are untouched), tu24 updated for the separate footer card; 10 mutants (8 caught, 1 equivalent: a credentials check that the host check also makes, 1 needed a stronger test; the span cap needed two).
- Not built: tables (they stay as text), syntax colours inside code blocks (the web has them; the terminal shows one colour), nested lists, task lists, strikethrough, a stream of half-written Markdown being reflowed gently as it grows (a block is re-read each frame; fine under the size limit, not measured), and the terminal-side display of the diff colouring (A-A27).

## Commands for scripts and CI (ledger A-A38)
- References (matrix A38, read as recorded there; the files were not re-read for this build): Cline `cline "prompt"` with `--json` NDJSON, OpenCode `run` with `--format json` and `session list/export`, Goose `run` and `session list --format json`, whose non-interactive mode refuses to run in approve modes instead of auto-allowing.

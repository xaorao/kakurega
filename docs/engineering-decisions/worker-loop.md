# Worker agent loop (experiment X1, decision D90)

## Target experience
The agent that does the work runs where it can do no harm, survives a crash without losing or repeating work, and shows the person every step, refusal and result.

## References
goose-agent 0.1.0-alpha.13 (Apache-2.0, crates.io; local clone commit 71dd9a9): `machine.rs`, `operation.rs` and the `tool.rs` provider trait read in full; `inference.rs`, `subagent.rs`, skills and the tests only surveyed. OpenHands' event store and Codex' resume were surveyed earlier (not re-read for this decision).

## What goose-agent offers
An event-sourced state machine: steps (operations and an inference step) produce effects, a runtime persists them and reloads the session, cancellation leaves unanswered tool calls with a synthetic "interrupted" response, and a `ToolProvider::call(session, request_id, call, emit)` seam fits our broker. It builds in about 30 seconds.

## Decision
Do not embed it for Milestone I. Costs measured: it requires rustc 1.94.1 (forced a toolchain bump), brings `rmcp`, `agent-client-protocol`, MCP result types and its own message model with metadata and visibility, and is an alpha API; the worker needs only a model call, a tool call and a checkpoint. A small loop (`kk-worker`, about 200 lines) keeps the same behaviours that matter: state is saved after every step; a crash resumes from the saved conversation; calls that had no answer are issued again under the same request id (read-only tools are repeatable and effect tools resolve through the effect ledger instead of running twice); cancellation and a turn limit save state first; a refusal is shown to the model and a fatal refusal (expired, budget, replay, no eligible route, policy error) ends the run. Revisit goose-agent when Milestone II needs subagents, skills and compaction. The toolchain stays at 1.94.1.

## Results (VERIFIED_BY_RUN)
- `cargo test -p kk-broker --test worker_loop`: 7 tests with a scripted model (SIMULATED) against the real broker: a full review with a labelled finding, crash then resume, refusals, turn limit and cancellation with resume, a hostile README that the model obeys, bad checkpoints, restore into a weaker session.
- Finding while writing the resume test: restoring a saved conversation into a fresh session started with a clean label, which would launder everything the conversation had seen. Checkpoints are now stored per job together with the taint at save time; loading one absorbs that taint into the new step and is refused if it exceeds the new worker's clearance (test w07).
- Sandboxed run on Linux: see the Linux results in TESTING.md (the real `kk-worker` binary and a hostile script).

## Not covered
Real-model behaviour (only the scripted route is used here; the local-model run is separate); concurrent steps; conversation compaction for long reviews; effect tools through the ledger; parallel tool calls in one turn beyond sequential execution.

## Loop detection in the worker (ledger E-A4)
- References, both read by me: OpenHands software-agent-sdk `openhands-sdk/openhands/sdk/conversation/stuck_detector.py` (commit 2f2cd2b, MIT; 515 lines, FULL): five scenarios over a window of 20 events since the last user message (identical action and observation repeated, identical action and error repeated, a monologue, an alternating A-B pattern, a context-window loop that is a TODO upstream); a nudge once per streak when it first reaches the threshold, a stop one repeat later; parallel calls count as one response. goose `crates/goose/src/tool_monitor.rs` lines 1-110 (Apache-2.0, commit 71dd9a9): refuse a call when the same name and arguments repeat more than a limit in a row. Not read: goose's tests and the TypeScript SDK port.
- Found by the full gate and not by the crate's own tests: comparing arguments as text made two calls with the same arguments in a different key order look different once another crate switched on JSON key-order preservation (cargo unifies that feature across the workspace). Arguments are now compared as values; the test passes with the feature on and off.
- Taken and changed: ours reads the saved conversation (so a restarted worker sees the same loop), counts a response as one assistant turn with its calls and their answers (parallel calls compare as a whole), and calls the same only when calls and answers are both the same (polling a status that changes is progress; argument key order does not matter). Told at three identical responses or six alternating, in a notice that is a user message starting with a fixed prefix and never counts as the owner's words; stopped at five or eight with a reason and the state saved. A new message from the owner starts the count again. Not taken: the monologue scenario (our agent has no free-text turns that continue a run: a turn without a call ends it) and the action-error scenario separately (an error answer repeats like any answer).
- Behaviour: `kk_worker::stuck::check` runs before every model call; the worker exits with code 6 and `{"worker_stopped": reason}` on standard error for `Outcome::Stuck`.
- Evidence: kk-worker st01–st06 (thresholds, told once, progress is not a loop, alternation, errors, owner message resets, parallel calls) and kk-broker w20–w22 against the real broker loop (a model repeating one call is told once and stopped after five asks with its state saved; one that changes course after the notice finishes; a stopped run resumed is stopped again at once because the saved conversation still shows the loop). 11 mutants, 9 caught; two are equivalent (the alternation guard against identical responses, which the repeat rule always pre-empts; and the save before stopping, which an earlier save already did).
- Not covered: a real model's behaviour after a notice (NOT VERIFIED: whether it changes course), the effect on a review's final report when a run is stopped (the exit code 6 is treated as a failed run like any other non-zero code; not specifically tested), thresholds chosen by judgement, not measured.

# Web workspace shell and companion API (task M1-02b)

## Target experience
A person opens a browser tab and works in a full workspace: projects, a task conversation with visible steps, a source viewer, an always-visible "where did my data go" panel, evidence review, release approval and capsule delivery. It must feel at least as fast and polished as OpenCode's and ChatGPT's web apps, while the page itself is never trusted with approvals or keys.

## References
- OpenCode (MIT, commit fe04656): `packages/app` (222k lines, SolidJS, Kobalte, Effect, Vite), `packages/ui` (58k lines, accessible component kit, i18n, strict typography rules), `packages/session-ui` (41k lines: message, timeline, tool rendering, diffs), `packages/server` (12.6k lines) and `packages/protocol` (5.4k). Read for this decision: package guidance for `ui`, `session-ui` and `app`; `server/src/auth.ts`, `cors.ts`, `pairing.ts`, `location.ts`; the dependency lists and directory structure of the four UI packages.
- Hermes `ui-tui` (React and Ink) and Codex `tui` (Rust) were only surveyed for the terminal decision (Milestone III), not for this one.
- Not read yet: `session-ui` message and timeline source, `protocol/src/api.ts`, `server/src/handlers`, the app's provider and session stores. They must be read before copying any code from them.

## Decision
- Stack: SolidJS with Vite and Kobalte primitives, on pnpm and Node. This matches OpenCode's UI packages (so timeline, tool and diff components can be adapted with credit under MIT) and OpenTUI (also Solid), so the terminal workspace in Milestone III can share the typed client and stores with the web. A fork of the whole `app` is rejected: it carries a coding-agent product, an Effect runtime and its own server. `ui` and `session-ui` pieces are adopted selectively after reading them, and restyled with Kakurega tokens (the "blank." direction, replaceable).
- The browser talks to the Rust companion over a typed HTTP and event-stream API defined by us. Nothing in OpenCode's server is reused.

## What OpenCode's local server does that we will not
- CORS accepts any `http://localhost:<port>` and `http://127.0.0.1:<port>` origin and any request without an `Origin` header. Another local web app, or a dev server on a different port, is therefore trusted (the WS01 attack).
- The password is optional and defaults to none; sessions are stateless 30-day HMAC tokens that cannot be revoked except by changing the password.

## What we take
- One-time pairing codes (16 random bytes, base64url, 5-minute lifetime, consumed on first use).
- Cookie names that include the port so two local servers do not collide.
- Same-origin check on cookie-bearing requests (`Origin` host must equal the request `Host`).
- The rule that browser code on non-secure origins cannot use `crypto.randomUUID`, `crypto.subtle`, clipboard or service workers: the companion is served only from a secure context (loopback HTTPS or localhost), and passkeys need that anyway.

## Companion API rules (tests WS01, WS02, WS05-WS07, new WS11-WS14)
Bind to loopback only; reject any `Host` that is not the exact companion host (DNS rebinding); `Origin` must equal the exact companion origin for browser requests, and a request with no `Origin` is accepted only with a native-client credential, never from a cookie; sessions are stored server side with a short lifetime and instant revocation; pairing codes are single use; every state-changing request carries a CSRF token bound to the session; approvals are never accepted from the browser session alone (passkey plus independent exact-bytes view).

## Not verified
Performance of Solid with long streaming transcripts at our scale; accessibility of Kobalte-based components under our themes; whether `@pierre/diffs` and `@pierre/highlights` are permissively licensed (to be checked before use).

## Search across kept conversations, and renaming one (ledger B-W07, G-GH-23)
- Reference: OpenCode `search.ts` mechanics as recorded in the matrix (multi-source, stale answers dropped, newest first); not re-read for this row, so NOT READ beyond the matrix. LibreChat's search is a Meilisearch service (not read) and would put conversation text in a second store, which this product refuses; ClaraVerse searches names only.
- Behaviour: `GET /api/sessions/search?q=` reads only conversations the owner chose to keep, inside the encrypted store. Every word of the question (up to 6, 64 characters each, 200 in all, plain text, no control characters) must appear, in any case, in the same conversation's title or turns. Results: up to 20, newest first, with up to two snippets of about 140 characters. A `%`, `_` or quote is just a character: nothing is a pattern and nothing reaches SQL. Withheld files are never in a conversation, so they cannot be found. `POST /api/sessions/{id}/rename` applies the same rules as a new title (1 to 80 characters, no control, direction or tag characters, no secrets) and the log records the length, never the title.
- The page ignores an answer to an older question when a newer one was asked (a sequence number, 200 ms pause); the terminal has `/find WORDS` and `/rename ID TITLE`.
- Evidence: kk-service sv89 (content, title, every-word rule, snippets, 6 hostile queries, 5 refused titles, 404, log, forgotten conversations disappear), kk-tui tu43, browser e2e 253/253 (a said word is found with its context, a word from another conversation finds nothing, rename shows in the list and in search). 15 mutants caught after two assertions were added.
- Not covered: an in-flight request is not aborted (older answers are dropped, not cancelled; the "one in flight" check of the matrix is not built); ranking beyond newest-first; archive; more than 20,000 turns (older turns are not searched); fork; Hindi read by a person.

## Message actions: copy, edit and branch, answer again (ledger B-W15)
- References: OpenCode `fork.ts` and `revert.ts` (fork a session before a prompt, the prompt returns to the composer), LibreChat `MultiMessage.tsx` sibling switcher and edit-and-resubmit as a sibling, AnythingLLM `HistoricalMessage/Actions`. Recorded in the matrix; NOT READ in source for this row. Taken: fork-before-prompt with the prompt back in the box, and a switcher between versions.
- Design that differs, on purpose: history is never rewritten. A branch is a new kept conversation holding a copy of the first N messages, with `parent` and `fork_at` recorded; the original is not touched. The switcher is the list of conversations that share a fork point (the original and its other branches at that message), so it needs no tree structure and survives forgetting any one of them (a branch whose original was forgotten stays whole).
- Behaviour: `POST /api/sessions/{id}/fork {at, title?}` creates a branch, 201 with its id. `at` is the number of messages kept (0 to the length); more is refused (400) and nothing is created. A title follows the rules of any title; none given means "<title> (branch)". The same project is kept. The 200-conversation limit applies and is now tested for new conversations too. `GET /api/sessions/{id}` returns `parent`, `fork_at` and `branches`; the list returns `parent` and `fork_at`. The signed log records that a branch was made, from which conversation and how many messages it kept, never words.
- Web: every message has Copy (exactly the text shown). Your messages have Edit and branch (the version opens with what came before and the message back in the box). Replies have Answer again (the version opens and asks the same question again). Both appear only in a kept conversation and while no reply is being written. A switcher card lists the other versions and says where the open one was branched.
- Evidence: kk-service sv92 (cut at the right message, original unchanged, continuing a branch leaves the original alone, siblings only at the same point, hostile points and titles, forgetting the original leaves branches, log record) and sv93 (limit); web unit br01–br04; browser e2e 281/281 three times in a row (counts of actions per message, Copy puts exactly the text on the clipboard, edit and branch, switching back to an unchanged original, answer again, both versions listed). 14 mutants on the service and web logic, all caught after two assertions were added.
- Not covered: branching a conversation that was not kept (nothing is stored to branch), branching in the terminal (the terminal has no kept-conversation switcher yet), the picker keyboard shortcuts for these actions, comparing two versions side by side.

## Colouring code (ledger B-W14)
- Reference: OpenCode `markdown.worker.ts` with `@pierre/highlights` (the matrix row; the worker and library sources were NOT read in this pass, so nothing is taken from them beyond the idea of text pieces with a kind). The matrix left open whether the library needs WebAssembly (Shiki's oniguruma does), which this page's content security policy forbids; that is still NOT VERIFIED, and was avoided by not using any of them.
- Built (`apps/web/src/highlight.ts`, `components/Code.tsx`): a one-pass scanner for Python, JavaScript/TypeScript, Rust, JSON, shell, SQL and C-family code (aliases such as py, ts, bash, go, java). It colours keywords, strings (single-line, multi-line and Python triple quotes), numbers, comments, function calls, JSON keys and shell variables with CSS classes (`tok-*`); no regular expressions that backtrack, no HTML is made, no inline style. The pieces always join back into exactly the input (fuzzed over 12,000 random strings built from tricky characters), so reading and copying are the same text, and each kind also changes weight, slant or underline so colour is never the only signal. A language it does not know, or a block over 60,000 characters, is shown plain. Used for fenced code in chat answers (the label is the fence's language) and for the reproducer in a finding (its check language).
- Measured: 5,000 lines (cut at the size limit) in a few milliseconds in Node, and 30,000-character hostile lines (backslashes, quotes, comment openers, parentheses) each under half a second in the test; the browser render time of a long block was not measured.
- Limits: it is not a grammar. JavaScript regular-expression literals containing `//` or quotes may be coloured wrongly, nested template expressions are one string, and Rust lifetimes read as the start of a string in some cases. Diffs (`DiffView`) and release file text are not coloured. A highlighter written for common shapes can be wrong; since colour never changes the text, a wrong colour misleads only the eye.
- Evidence: web unit tests hl01–hl09, the browser suite (341/341: coloured reproducer with keyword, string and call spans, text exact, only spans and no inline style, axe, screenshot read), 10 mutants (7 caught, 1 caught after a new test, 2 equivalent: an alias lookup guard that the language lookup already makes harmless, and decimal numbers that are merged back together).
- Not covered: the copy button's output was not re-tested (it copies the original string as before), mermaid and other special blocks, and an incremental tokenizer for answers that are still streaming (a block is coloured as it grows, which re-scans it each time; fine under the size limit, not measured).

## Long lists: measured, and no virtualiser (ledger B-W18)
- Reference: OpenCode `virtualizer.tsx` (`@tanstack/solid-virtual`, MIT) with a measurement cache and deferred mounting of heavy bodies (matrix W18; the files were NOT read in this pass). The matrix's condition was to profile before adopting anything, so this is the profile.
- Method (`tests/e2e/long_lists.mjs`, run by the gate): the real page in headless Chrome against the real service; the Memory screen given 5,000 notes by a mocked list answer, and the Chat screen driven through 400 sends (the kept-conversation limit) with an instant mocked model answer so the page, not the model, is what is timed; DOM nodes, JavaScript heap and the gaps between animation frames while scrolling the whole page down and back are recorded. Machine: this Mac, one headless Chrome; the figures are for comparison, not a promise.
- Measured (VERIFIED, this machine): Memory with 5,000 notes shown after 0.36 s, 40,807 DOM nodes, 66 MB heap, longest frame while scrolling 35 ms. Memory with 20,000 notes: 1.3 s, 162,950 nodes, 254 MB, longest frame 143 ms. Chat: the page-side cost of one send was 11 ms at turn 1, 10 ms at 100, 46 ms at 300, 98 ms at 500 and 384 ms at 1,000 turns (20,095 nodes, 122 MB, longest frame 43 ms), so it grows faster than the length but is small where chats really end: a kept conversation stops at 400 turns, where the cost is about 60 ms.
- Decision: EXCLUDE a virtualiser for now. It is not needed at the sizes the product allows, and it would break things the page relies on that need real elements in the page: the browser's own find, the in-page transcript search and match highlighting, text selection across messages, copying, screen readers reading the whole conversation, and keeping the view at the bottom while an answer streams. It would be paid for by every user to help a case (an unkept chat of many hundreds of turns, or tens of thousands of notes) that works, slowly.
- Revisit when: a send costs more than 300 ms at the longest conversation the service keeps, the Memory list is allowed beyond 20,000 notes, or a frame over 200 ms is measured. The gate's check fails at 5 s for a send or 500 ms for a frame, which only catches a screen that has become unusable.
- Not measured: a long review page with very many findings, the Activity log at its limit, a slow computer, Firefox and Safari, and memory over hours of use.

## Approval expiry shown and failing closed (ledger B-W36, G-GH-36)
- What already held (VERIFIED in code, not changed): every release carries a deadline (`ReleaseDraft.expires`, 24 hours from when it was made), the deadline is part of the signed approval statement, and the kernel (`kk-review/src/release.rs`, the lease check) refuses to approve or deliver at or after it (`LeaseError::Expired`). The screens said nothing about it: an owner learned of an expired release only from a refusal.
- Built: the web release tab's approval card says how long the release can still be approved ("This release can be approved for another 23 h 59 min"), warns in words and colour when ten minutes or fewer remain, and when the deadline has passed shows an alert and disables both Request approval and Sign and deliver. The countdown runs against the service's clock (the release answer now carries `server_time`) and the page's clock difference is taken once, so a computer with a wrong clock does not change what is said (the browser suite sets the page's clock three days ahead and still reads the right figure). A deadline that is missing or not a number is never shown as valid. ## A large reply cut off by an unread request body (CONFIRMED, fixed) (ledger B-W44 area)
- How it was found: the gate failed on `sv142` (restoring a notes backup over a megabyte), and the same test failed or hung in about one full parallel run in four, never alone. An earlier session had logged it only as "flaky".
- Evidence trail (VERIFIED): the failing client got `200` with `Content-Length: 1590180`, received 1.28 to 1.45 MB, then "Peer disconnected" about 2 ms after the headers; no panic or error on the server; not a time limit; not file descriptors, ports or threads (measured); not the review-limit tests, nor the detector changes (the failure rate was the same without them).
- Cause: the sealed export is a POST with a two-byte body (`{}`) that its handler never reads, and it works for about 180 ms on a worker thread. If the body arrives in a separate packet it stays unread in the connection. When the server closes the connection after the large reply, an operating system that closes a socket with unread bytes sends a reset, and the reset discards the part of the reply the client has not read yet. The same can happen to any large reply to a POST whose handler ignores its body, on a busy computer.
- Proof (VERIFIED): `sv147` sends the headers, waits 700 ms, sends the body, and reads the reply slowly. Without the fix it fails every time (6 of 6, "Connection reset by peer" after 1,161,132 bytes); with it, it passes. The full service suite then ran 40 times with no failure, no hang, against about 1 in 4 before.
- Fix: the guard (`crates/kk-companion/src/app.rs`, `run_handler`) reads the body itself before any handler when the declared length is 1 byte to 64 KiB, for the app and for the extension door. Larger bodies (uploads, restores) keep streaming to the handlers that read them; chunked bodies and requests without a body are untouched; a body that stops early is refused with 400 `BAD_BODY`.
- Evidence: `crates/kk-companion/tests/body_guard.rs` bg01 (the reply arrives whole with the body together and late, four rounds), bg02 (bodies of 1, 2, 10, 65,535 and 65,536 bytes arrive intact), bg03 (65,537 bytes up to 1.5 MB still reach the handler), bg04 (chunked and absent bodies), bg05 (a body that stops early: clean 400, the server carries on), bg06 (a slow body on one connection does not hold up another), bg07 (the extension door); `sv147` for the backup endpoint. 5 mutants caught (buffering off, a limit of one byte, the refusal's status and code, the extension door skipping the read); the limit of 64 KiB itself cannot be seen from outside (a larger buffer behaves the same) and is chosen to bound memory.
- Not covered: other large replies were not each tested (the guard covers them all by construction); a body that arrives slowly forever holds its connection as it already did for the handlers that read bodies; HTTP/2 (the server speaks HTTP/1.1 only).

## Idle connections could stop the service (CONFIRMED by a probe, fixed) (ledger B-W36 area)
- How it was found: the large-reply bug showed that the server's connection handling was the stock `axum::serve` with no limits at all. A probe started the real `kaku serve` with the 256-descriptor limit that a program launched from the desktop typically inherits, opened 600 idle connections from a plain script, and asked for `/api/health`.
- Result before (VERIFIED): with the idle connections open the health check timed out, and the service stayed unresponsive until the script closed them. The server never closed an idle connection by itself. Any program on the computer, or a client that leaks connections, could do it.
- Fix (`crates/kk-companion/src/lib.rs`, `serve`): a bounded accept loop on hyper, replacing `axum::serve`. At most 128 connections are served at once (the rest wait in the operating system's queue, which costs no descriptor); a connection that does not send its request head within 10 seconds is closed; each connection serves one request and is then closed (`Connection: close`), so no client can send a request down a connection the server has just closed; on shutdown connections finish and any left after five seconds are dropped. The limits are options, for tests.
- Result after (VERIFIED on the real binary, same 256 limit): 150 idle connections delay a real request by about 10 seconds (the timeout) and it is then served; after 600 attempts everything recovers by itself within 12 seconds, and the next health check is immediate.
- A regression I checked for and avoided: the terminal client keeps a pooled connection for 15 seconds, so an idle limit of 10 seconds could have made the first request after a pause fail. Raced 120 times at the boundary with no failure, but a rare race is still a defect, so keep-alive is off and the class cannot occur (`cn07` pins the pooled-client case).

## Documents: meaning as well as words, kept vectors (ledger B-W26, second part)

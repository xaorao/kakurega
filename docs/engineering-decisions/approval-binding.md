# Approval binding (II-12): what proves the owner approved this exact release

## The gap an outside reviewer found
A Touch ID or terminal prompt proves a person was present. It does not prove they approved this recipient, these bytes, this policy, once. Until now the service accepted an approval from anyone holding the local admin token who knew the digest prefix.

## Contract (framework-independent, in the kernel crates)
- Statement: `{approval id, job, full release digest, recipient, policy version, expiry, one-time nonce}` in canonical JSON, signed as a DSSE envelope (type `application/vnd.kakurega.approval+json`) with an Ed25519 approver key (`kk-evidence::approval`).
- The service creates the nonce with the approval. Once any approver key is enrolled, `approve` requires a proof that verifies against an enrolled key and equals the service's own statement byte for byte; a changed recipient, digest, policy, expiry, approval id or nonce voids it. An old proof cannot be replayed on a later approval.
- Changing who may approve (enrol or revoke) also needs a fresh (120 s) signature from an enrolled approver over the action and the key, so the admin token alone cannot add its own key or remove the approver and fall back to the old path. The first enrolment is the trust root (trust on first use through the local admin token).
- Both terminal tools sign: `kaku approve` and the terminal workspace (`kaku`) use the key at `<data dir>/approver.key` (created by `kaku approver enroll`, mode 0600, refused if others can read it) and refuse to send anything when the service requires a proof and no key exists.

## What this does and does not give
- Gives: a compromised web page, a stolen session, or a leaked admin token without the key file cannot approve or change approvers; every approval is bound to its exact release and cannot be replayed.
- Software key (default): a file, so malware running as you can read it.
- Secure Enclave key (`kaku approver enroll --enclave`): a P-256 key created inside the Secure Enclave by the Swift helper `spikes/enclave/kaku-enclave.swift` (CryptoKit, AppKit). The blob on disk is encrypted to this Mac's enclave. Proofs are `p256-se` envelopes verified by `kk-evidence::hw`.
- The helper is a trusted approval step, not a signing oracle. A caller gives it only an approval id. It fetches the release from the kernel itself (admin file in the data dir), accepts only a statement in the exact canonical form (printable-ASCII recipient, no quotes, backslashes or look-alikes), requires the statement's approval id, digest and recipient to match the kernel's details, refuses expired approvals, shows its own native dialog derived from the statement it will sign (default button Refuse), and only then asks the enclave to sign those exact bytes. It has no command that signs caller-supplied bytes. Approver changes (enrol, revoke) are built by the helper from an action and a key id, behind their own dialog. One dialog at a time (file lock); a killed helper leaves no state.
- The shipped helper has no automatic-approval switch; a separate test build (`build.sh --test`, compile-time flag) replaces only the dialog so the hostile cases can run unattended. The test build must never be shipped.
- What the user's authentication proves: with `--presence` the key uses the user-presence policy, so every signature needs Touch ID OR the account password. That is presence, not biometric-only; a biometric-only policy was not chosen because a Mac mini has no sensor. Neither proves the user understood the bytes; the dialog plus the signature over exactly what it showed is what binds the decision.
- VERIFIED on this Mac mini (M4): enrolment, signing, Rust verification of a real enclave signature, 48 hostile helper checks (changed digest, recipient, approval id, version, ordering, extra fields, expired, look-alike and bidi recipients, quote and backslash, hostile ids, missing admin file, unknown approval, refusal, concurrent dialogs, kill and retry, altered or damaged key blobs, no generic sign command), the terminal and Electron flows with an enclave key, and the real native dialog shown by the shipped helper (screenshot inspected: Refuse is the default). NOT VERIFIED: the `--presence` prompt and a real click on Approve (owner), Windows and Linux (TPM or platform keystores), the Tauri shell signing, a notarised build. Limits: a recipient that is not printable ASCII cannot be approved through the enclave helper; malware that can run the helper still cannot sign without the owner clicking Approve and passing presence, but a key enrolled without `--presence` needs only the click.
- Mac minis have no Touch ID sensor: presence falls back to the account password unless a Touch ID Magic Keyboard is paired.
- Legacy path: with no approver enrolled the old admin-token approval still works and the service says `requires_proof: false`. Revoking the last approver reopens it, by a signed owner decision.

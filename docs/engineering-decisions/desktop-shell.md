# Desktop shell: Tauri or Electron (Milestone II, first decision)

## Target experience
A native app that opens straight into the workspace, runs the kernel on the user's own machine, shows approvals in a window no agent or page can draw over, and uses the operating system's own authentication (Touch ID on macOS) for the approval signature.

## Strongest references
Electron (Chromium and Node in every app), Tauri v2 (Rust core, system webview, capability-scoped commands), OpenCode desktop (Electron, MIT, `private-ai/inspiration/opencode/packages/desktop`, commit fe04656; an earlier version of this note wrongly said Tauri), Codex app server. Read in full for this note (VERIFIED by reading): `main/index.ts`, `desktop.ts`, `ipc.ts`, `ipc-transport.ts`, `preload/index.ts`, `windows/security.ts`, `service/sidecar-credentials.ts`. NOT read: window creation details beyond the flags, lifecycle, plugins, updater, packaging config.

## Facts gathered (live search, this session)
- OBSERVED: WKWebView (what Tauri uses on macOS) runs in the app's context; passkeys there are limited to the app's associated web domain, and a browser-grade entitlement is reported anecdotally. Tauri-specific WebAuthn support was NOT found.
- OBSERVED: Electron adds a Touch ID platform authenticator only from Electron 42 through `app.configureWebAuthn`, and the in-renderer path needs an https origin that satisfies the passkey's relying-party id; Linux has no native path; a community MIT module (`electron-webauthn-mac`) uses Apple's AuthenticationServices.
- Both facts say the same thing for us: a page-level WebAuthn prompt is the wrong layer for approvals on a loopback app. The approval prompt and key belong in the shell's native layer.

## What OpenCode's Electron shell does well (VERIFIED by reading, MIT, adaptable with credit)
- Windows use `contextIsolation`, `sandbox`, no Node in the renderer; UI served from a private custom scheme.
- Navigation policy: new windows denied, off-origin navigation sent to the system browser; permission allow-list checked against the requesting URL and main frame.
- The renderer never sees the sidecar credential: the main process adds the Authorization header only for the top-level renderer frame (embedded pages in the same session do not inherit it).
- IPC over a transferred MessagePort per window instead of broad `ipcRenderer` exposure; CLI bundled outside the asar; first window shown before the heavy bundle loads.
## Weaknesses to beat
- The IPC port is handed to the window on every `did-finish-load` without checking the frame URL in the code read (a navigated or embedded page could receive it); we check the frame origin and top-level status before handing anything over.
- The main process is a large Effect-TS dependency tree; ours needs a small surface (window, sidecar, native approval).

## Decision (INFERRED, to be proven by a spike before it is final)
Leaning Tauri v2, but the strongest reference being Electron (MIT, forkable patterns above) keeps this OPEN until the spike measures both: Tauri v2, with the kernel crates linked into the Rust core (same language, no second privileged runtime, no Node main process), the existing web app loaded from the companion's loopback origin, and approvals done by a native window plus the OS authentication API through Rust (LocalAuthentication and the Keychain or Secure Enclave on macOS). Reasons: one language and one permission model across kernel and shell; smaller attack surface; capability-scoped IPC; no dependency on WebAuthn support inside a system webview.
Risks to test before committing: LocalAuthentication from a Tauri app without a Developer ID, webview differences across macOS, Linux (WebKitGTK) and Windows, window-overlay and screen-capture protection for the approval window, auto-update signing.
Fallback if the spike fails: Electron 42+ with the native approval module, same kernel as a child process.

## DECISION (final for now): Electron
Measured on this Mac (3 runs, Electron 45.2.2, `/tmp` harness, process tree incl. the companion): app bundle 253 MB; time from launch to the usable workspace 0.73 s, 0.95 s and one cold 3.7 s; memory about 454 MB across 5 processes.
Why Electron over Tauri (reasons that are verified, not guesses):
1. Our whole quality standard is real-UI testing with Playwright, axe and screenshots; Playwright drives Electron natively (13 desktop checks already run this way) and cannot drive a macOS WKWebView shell, so Tauri would leave the desktop UI less testable.
2. The strongest reference shell (OpenCode, MIT) is Electron and its hardening patterns are adoptable with credit.
3. Electron 42+ has a Touch ID platform authenticator and `systemPreferences.promptTouchID` is what the shell uses today; the native approval is working in the real window (stubbed OS prompt; real Touch ID is II-03).
4. One Chromium everywhere: no WebKitGTK versus WKWebView differences to test on Linux and Windows.
Cost accepted: 253 MB bundle and about 450 MB memory. Tauri was NOT built or measured (disk and time spent on the working path), so the claim that Tauri would be smaller is a reference-based expectation, not our measurement. Revisit if size or memory becomes a user complaint.

## Spike acceptance (all met except real Touch ID and the Tauri measurement, see above) (before this is called decided)
1. A Tauri window opens the web app from a loopback companion started by the shell, with pairing automatic and no URL typed.
2. A native approval window shows the exact file list and digest and requires Touch ID; a page script cannot trigger, hide or answer it (hostile test).
3. The shell survives kernel restart and shows recovery state.
4. Build size, start time and memory measured against a minimal Electron shell.

## Not done
Spike not started; source of OpenCode's desktop package not read; Windows and Linux not tested; disk is tight (about 5 GB free), so the spike builds with a shared target directory.

What the Tauri spike has: a window on the loopback app with an origin-locked navigation handler, no capability granted to any window (a page can call no native command), and a native approval dialog that approves or refuses through the same admin API. What it does NOT have: Touch ID, signed approvals, hardening review of a packaged build.

### Evidence-based reading (owner decides: II-04)
- Efficiency: Tauri is about 75 times smaller and uses about 2.2 times less memory with equal perceived start-up. That is material for an app people leave running.
- Boundary: with no capability granted, a page in the Tauri webview has no IPC at all; the shell is Rust like the kernel, with no second runtime. Electron needs its sandbox, preload, fuse and port-handoff discipline to reach a comparable position.
- Cost of switching: re-do the 13 shell checks in WebdriverIO, add the native approval and Touch ID path (needed for both shells), and accept WKWebView differences, with Windows and Linux webviews untested.
- Recommendation: move the shipping shell to Tauri v2 once it passes the same boundary checks and the approval binding (II-12) is built in Rust, keeping the Electron spike as the reference until then. This is a recommendation from measurement, not a decision: the owner accepts or rejects it.
- Kernel and approval contracts stay framework-independent (`/admin/approvals` and the digest), so the choice can be changed without rebuilding the security architecture.

## Same attacks on both candidates (II-13)

Both shells were run through the same renderer-compromise script (session cookie, admin endpoints, CSP, native-command access, window.open, navigation). Electron: `node tests/e2e/desktop_attack.mjs` (19 checks) driven through Playwright. Tauri: `python3 tests/e2e/tauri_attack.py` (9 checks) driven by a test-only feature that evaluates the script inside the real WKWebView and reports through the URL fragment (the window title does not mirror document.title).

- Result: the page is equally contained in both. Every admin endpoint refuses it, the CSP blocks inline script, eval, remote scripts and beacons, no window opens, and navigation is refused or reversed. In Tauri the page can see `__TAURI_INTERNALS__` but every native command (dialog, window, app, fs, an unknown command) is refused because no capability grants anything.
- Difference found: Electron let a page navigate to `about:blank` (fixed with a did-navigate guard); Tauri's `on_navigation` refused it by default.
- Not equal yet: Electron has asar integrity validation, fuses and a tested tamper response (II-13b, II-13c). Tauri has no counterpart built or tested (code signing of the binary, integrity of the frontend, update path). That gap, not the attack surface of the page, is what remains to compare.
- The decision (II-04) is still the owner's.

## Crash recovery (added)
- Companion exit while the app is open: restarted up to 3 times in 5 minutes with growing waits (0.5 s, 1 s, 2 s). The companion takes a new port each start, so the shell re-reads `admin.json`, asks for a new pairing code and loads the window with it; the approval poller reads the current connection. Past the limit the owner gets a plain message and nothing restarts. Anything running at the crash is stopped (job state is not resumed); the owner is told by a system notification, nothing was sent anywhere.
- Window process crash (`render-process-gone`, not a clean exit): the window is reloaded (same session, no new login); the same 3-in-5-minutes limit then a message. An unresponsive window asks Wait or Reload.
- Evidence: ds10-ds11 (policy), `tests/e2e/desktop_recovery.mjs` on real Electron on the Mac (7/7) and in the Linux VM (7/7): kill -9 of the companion, `forcefullyCrashRenderer`, repeated kills to the limit. Mutations: no reload on renderer crash fails the run; removing the limit fails two checks.
- Not covered: Windows; a hung (not dead) companion; resuming an interrupted review; the unresponsive dialog (not driven).
- Harness note: `desktop.mjs` needs `spikes/enclave/build.sh --test target/debug/kaku-enclave-test`; without it two enclave checks fail (precondition, not a product defect).

## Per-launch shell secret and pairing throttle (ledger F-E6)
- Reference: OpenCode `sidecar-credentials.ts` pattern (read earlier, trace row on the desktop shell; MIT): the shell main process holds a per-launch credential and adds it to its own window's requests. Not copied; rebuilt for our companion.
- Found by reading our own gate (VERIFIED by a failing test first): after 5 wrong pairing codes the companion refused even the RIGHT code for 60 s, so any program on the computer could keep the owner out of their own app by sending wrong codes in a loop. The code is 128 random bits, so the lockout never protected anything. Now the code is checked first; only wrong guesses are throttled; a test (ws13c) guards the 128-bit premise, because shortening the code would make this unsafe.
- Decision: BUILD. The desktop shell generates 256 random bits for every companion it starts, gives them to `kaku serve --shell-secret-stdin` on stdin (not the environment or arguments, which review workers inherit and other programs can list), and adds `x-kk-shell` only to requests to the companion's own origin (policy.mjs `withShellSecret`; a lookalike origin or a page-supplied header never gets or keeps it). The companion answers 403 `SHELL_ONLY` to anything else except `/admin/` (its own bearer token) and `/ext/` (its own pairing). Constant-time compare; at least 32 characters or the companion will not start.
- What it buys: another program on the computer cannot load the page, probe `/api/*`, try the pairing door, or use a stolen session cookie. What it does NOT buy: a program running as the same user can still read `admin.json` and mint its own pairing through the admin door; that is the same trust domain and the owner's operating system account is the boundary.
- Evidence: kk-companion ws13b, ws13c, ws20–ws22 (13 mutants caught, one equivalent in serve), desktop unit ds20–ds21, real Electron: desktop.mjs 22 checks including five outside-program refusals, desktop_attack.mjs 23/23 (its old control "a process with the cookie is served" now asserts refusal), desktop_recovery 7/7, desktop_packaged 7/7, desktop_fuses 7/7, Linux in the VM (`scripts/desktop-linux`) all pass; 3 Electron-wiring mutants caught.
- Not covered: Windows desktop; the browser workspace (`kaku serve` for a normal browser) has no shell secret by design, so its protection is still the pairing link, cookie and Origin checks. The attack suite's later cookie attacks now meet `SHELL_ONLY` first; the underlying Origin, CSRF and cross-site checks remain proven by the companion tests and the browser e2e.

## A companion no longer outlives a desktop app that was killed (found while testing F-E6)
- Found: a `kaku serve` started by the desktop shell was still running two hours after its test Electron had been killed. Before the shell secret the companion had no way to notice its shell had died (`KAKU_EXIT_WITH_PARENT` was never set by the shell), so a crash, a forced quit or a power cut left a service running with nobody holding its window. This is older than the shell secret; it was seen because the test debris was still there.
- Fix: the shell keeps its end of the pipe that carried the secret open for its whole life. `kaku serve --shell-secret-stdin` reads the secret, then keeps reading the pipe; when it reaches the end (the shell is gone, however it went) the service removes its admin file and exits (within a second). Tests: kk-cli ss02 (stays while the pipe is open, leaves and removes the admin file when it closes), `tests/e2e/desktop_forcequit.mjs` (real Electron on this Mac and in the Linux VM: the same companion keeps running for five seconds while the app is open; after SIGKILL of the app it is gone in about one second and so is `admin.json`). The mutant "the service ignores a closed pipe" is caught by both. The mutant "the shell closes the pipe right after the secret" is equivalent under Electron: Electron's half-closed stdio is not seen by the child, so it is not detectable there; the pipe closing when the process dies is what the test proves.
- Not covered: a shell that is stopped (SIGSTOP) rather than killed; Windows.

## Keeping Electron itself current (ledger F-E8)
- Policy read from the live Electron page (electronjs.org/docs/latest/tutorial/electron-timelines, "Version support policy"): the latest three stable major versions are supported, only the newest release of each of them receives a fix, and the oldest supported line gets security fixes only. So the pinned version must be the newest release of one of the newest three majors; anything else may be missing a security fix.
- Our policy: the pin in `apps/desktop/package.json` is exact (no range), is the newest release of the newest or the previous major, and is moved to the newest release of its line before every release and whenever the checker says it is behind. `python3 scripts/check_electron.py [--strict]` asks the npm registry and reports current, supported, behind or unsupported (exit 1 for unsupported, and for behind with `--strict`; offline it says it could not check). Its comparison is tested offline (`--selftest`, run by `scripts/test`); the registry call is not part of the build because a build must not depend on the network.
- Applied now: the checker found the pin at 45.2.2 with 45.2.3 out, so the pin was moved to 45.2.3 and the desktop suites were run on it: window and approval flow 22/22, attack suite 23/23, fuses 7/7, recovery 7/7, force-quit 4/4, packaged app 7/7. The release notes of 45.2.3 were read later (below).
- Not covered: a schedule that runs the checker by itself (it is a command to run before a release; nothing runs it on a timer), the Linux package build on the new version (needs the VM suite's packaging step; the gate's VM suites ran green but do not rebuild the package), Windows.

## Why the hardened-app check was flaky (found by bisecting)
- Symptom: `desktop_fuses.mjs` ("the app still starts and its companion serves the workspace") failed on and off, then every time. The app never became ready and printed nothing.
- Bisect: a plain copy of Electron starts in 3 seconds; flipping any single fuse (RunAsNode, NODE_OPTIONS, inspect arguments, file-protocol privileges, cookie encryption) with only the main program re-signed leaves a bundle that hangs; flipping and then signing the whole bundle (`codesign --force --deep --sign -`) starts every time. The packaging script already signs the whole bundle after setting fuses; the test did not, so it tested a bundle the product never ships.
- Fix: the test now signs the bundle the way packaging does (3 runs in a row and the packaged-app test pass). The earlier cache and disk explanations were wrong or incidental; the app-owned files now live inside an explicitly chosen data folder anyway.
- NOT VERIFIED: why it worked before today; an operating-system update is possible (the machine reports macOS 26.6.1) but no evidence was gathered.
- Update after more measuring: the deep signing alone did not remove the flake. An unmodified copy of Electron that is only re-signed ad hoc hangs on its first launches (twice in a row in one measurement, then starts within a second; the stock copy with its original signature starts in three seconds every time). So the two desktop bundle checks now repeat a launch that is expected to work and has not produced its companion within 15 seconds (up to six launches); tampered bundles are never repeated, since they must refuse to run. Cause NOT VERIFIED (a first-launch security assessment of a newly signed bundle is suspected, not shown). The product impact is limited to ad-hoc signed builds; a release signed with a real identity and notarized has not been tried because that identity does not exist yet (listed in HUMAN.md).

## An enrolled signing key is required in the packaged app (ledger F-E14)
- Decision: of the two approval paths the desktop shell disclosed (a confirmation on this computer, or a signature from an enrolled key), the packaged app now allows only the signed one. `kaku serve --require-approver` closes the unenrolled path: until a key is enrolled, approving a release is refused with `NO_APPROVER` ("run `kaku approver enroll` first") and changes nothing; once a key is enrolled the ordinary rule applies (the signature is required, `PROOF_REQUIRED` without one). `/api/privacy` reports `signing_key_required`. The packaged app starts its companion with the flag; the development app and a plain `kaku serve` do not.
- Finding on the way: `app.isPackaged` is false for this bundle, because its program is still called Electron. "This is the packaged app" is decided by its code being read from an archive (`app.getAppPath()` ends with `.asar`). Nothing else relied on `isPackaged`.
- Evidence: kk-service sv119 (refused with NO_APPROVER and nothing delivered; the page's facts say the key is required; after enrolling, the refusal changes to PROOF_REQUIRED), the packaged-app suite checks the companion's command line, and the development suite (22 checks) shows the other path still works; 4 mutants caught (check removed, flag ignored, enrolled key not satisfying it, flag dropped from the shell), one of which needed the enrolment step added to the test.
- Consequence for a person: a packaged build cannot approve anything until `kaku approver enroll` has been run once. The desktop shell does not yet say so when it gets the refusal (it shows the refusal as outcome "refused"); the message is now built (next paragraph).
- Message built (closes the item above): the approval detail now carries `approver_missing` (the approver is required and none is enrolled). The shell then asks the owner nothing, posts nothing (the approval stays waiting) and shows one notification, "A release is waiting, but approving needs a signing key. Run `kaku approver enroll` once in a terminal, then approve the release there with `kaku approve`." It is reported once per approval. Evidence: sv119 (the flag is true before enrolment and false after), shell unit test ds04b (no confirmation asked, nothing posted, reported once, and a false flag runs the ordinary journey); 6 mutants caught, one of them only after the false-flag case was added. NOT exercised: the real notification on screen.

## The desktop app made complete: menu-bar item, notifications, two languages, a self-contained package and an installer

### Target experience
Kakurega keeps running when its window is closed, as a Mac app does: a menu-bar item says it is running and how many things wait for the owner, and opens the window, the "Waiting for you" screen, or quits. When something needs the owner (an approval, a finished review, a review that stopped, an expert's question) and the window is not in front, the operating system shows a short notice that says only that something waits; clicking it opens the window on that item. The shell's own words (approval window, dialogs, notices, menu) follow the system language, English or Hindi, like the web app. A person downloads one zip, checks it against the published SHA-256 value with one command, and gets an app that carries everything it runs.

### What was built
- Menu-bar item (`apps/desktop/src/tray.mjs`, wired in `main.mjs`): a template icon drawn as a PNG at 16 and 32 pixels (black and transparency, so macOS draws it in the bar's colour), the count beside it, and a menu with the status ("Kakurega is running", what waits, or "has stopped"), Open Kakurega, Waiting for you (n), "Tell me when something needs me" (remembered in `shell.json` in the app's data folder) and Quit Kakurega. The menu is rebuilt only when what it shows changed, so a menu the owner has open is not replaced under the pointer. On macOS closing the window hides it and the companion keeps running; Open, the Dock icon, a second launch and a notice bring the same window back. Elsewhere closing the window still quits. Quit ends the companion and now also removes its admin file when that file belongs to the companion this shell started (found by the new test: a normal quit left `admin.json` with a dead port and token behind).
- Notifications (`apps/desktop/src/inbox.mjs`): the web app's rules: the same four announced kinds, the same "same item" key, at most three per update, nothing that was already waiting at start, never while the window is in front, and an item that arrived while the owner was looking is not announced later. The words are the web app's `notify.*` (a test compares them with `apps/web/src/locales/*.ts`). Each item is cut to its kind and ids as soon as it is read, so recipient, title, question and "what" text cannot reach a notice. A click opens `#/job/<id>`, `#/team/<id>` or `#/inbox`; only ids matching `[A-Za-z0-9_-]{1,64}` are put in an address. The page's own browser notifications stay impossible inside the window (every permission is refused), so nothing is shown twice.
- How the shell learns the inbox: through its existing admin token only. It asks `GET /admin/inbox` first; this service answers 404 (the route does not exist yet), and the shell then works the reviews' part out of `GET /admin/jobs` by the service's own rules (ready and not delivered: approval waiting, approved, or ready to review; failed unless stopped by the owner). Team runs are not visible through any admin route, so **a team's question is not announced and team items are not counted yet** (see "Needed outside the desktop").
- Two languages (`apps/desktop/src/strings.mjs`): every dialog, notice, the approval window's text and deadline, and the menu, in English and Hindi, using the web app's Hindi terms. The language is the first of the system's preferred languages that is English or Hindi (`app.getPreferredSystemLanguages()`), or the app locale when the app is started with `--lang`. The English text is unchanged word for word.
- Self-contained macOS package (`apps/desktop/scripts/package.mjs`, `apps/desktop/src/bundle.mjs`, `scripts/package-desktop-macos`): kaku and the shipped Secure Enclave helper in `Contents/MacOS`, the web interface in `Contents/Resources/web`, and their SHA-256 values in `bundle.json` inside the asar. The shell checks each part before it uses it (kaku at start and before every restart and signature, the web folder at start, the helper before each signature) and refuses to start, naming the part, when one differs. `KAKU_BIN` still overrides kaku for development (the bundled kaku is then neither used nor checked); a `--ui-dir` in `KAKU_ARGS` overrides the web folder. Packaging refuses the test build of the enclave helper (it approves without asking), signs each nested program before recording its value (ad-hoc signing of the same file under the same name gives the same bytes; measured), and checks after the final signature that every part still has its recorded value. A zip made with `ditto` and a `.sha256` file are written beside the app.
- Installer (`scripts/install-desktop-macos [--clear-quarantine] ZIP SHA256 [DESTINATION]`): compares the zip's SHA-256 with the published value (64 hexadecimal characters, or the .sha256 file) before anything else; unpacks only after a match, into a new private temporary folder; requires exactly one `Kakurega.app`, no link pointing outside it, and an intact signature (`codesign --verify --deep --strict`); refuses to replace a running copy; replaces an installed copy as a whole and puts it back if the move fails. Nothing from the archive is executed. It says plainly that the app is signed ad hoc only and not notarized, and how to open it the first time. `--clear-quarantine` removes the download mark only when asked, after every check.

### What the integrity of the bundled parts covers, and what it does not
- Covered (VERIFIED by tests): a changed, truncated, missing or replaced kaku is not started; a file added to, removed from or renamed in the web folder, or a link placed in it, stops the app before the companion starts; a changed enclave helper is not run for signing (in code and in the unit tests of `checkPart`; NOT exercised end to end, because the packaged app cannot be driven by Playwright with its inspector fuses off). The values sit in the asar, whose header Electron checks against the hash in `Info.plist`.
- Not covered: the chain ends at an ad-hoc signature. Someone who can write to the installed app (the same user, or anyone with admin rights) can change a part, rebuild `bundle.json` and the asar, write the new hash into `Info.plist` and sign the bundle again ad hoc; nothing in the bundle can tell. A Developer ID signature with notarization would anchor the chain to an identity; it does not exist yet (HUMAN.md). The check is made before each use of a part; a file changed after the check (while kaku runs, or in the web folder while it is served) is not noticed. Measured cost: about 50 to 100 ms per check of the 124 MB debug kaku and the web folder.
- macOS notices from an ad-hoc signed app: NOT VERIFIED on screen. Electron's docs say an unsigned app cannot deliver them; this one is signed ad hoc, and whether macOS 26 delivers them was not observed (the tests replace `Notification.show`, so nothing reaches the notification centre). A `failed` event is written to stderr.

### Screen capture into chat: not built; what it would need
- The page cannot do it under the current policy, by design. `navigator.mediaDevices.getDisplayMedia()` in the page needs a `setDisplayMediaRequestHandler` in the main process (there is none in `main.mjs`), and every permission request and check is refused: `policy.mjs:9-11` (`allowPermission()` returns false), applied at `main.mjs:309-310`. Allowing it would hand screen pixels to the page, the least trusted part (where a prompt-injected or compromised script runs); with the handler pattern in Electron's documentation the first screen is granted with no further prompt. That conflicts with the shell's invariant that every permission request is refused and with the attack suite's permission checks.
- A version that does not conflict: capture in the main process with `desktopCapturer.getSources({ types: ["screen", "window"], thumbnailSize })`, started only from the shell's own menu (or a global shortcut it owns), shown in a native confirmation dialog first, then sent to the companion as an attachment. No bridge, no page permission, and the page never sees the pixels before the owner said yes. Pictures are already read by the service's OCR (`kk-parse`, `Medium::Picture`), so it would arrive as text, with the attachment checks applied.
- What blocks it outside the desktop: (1) `/api/attachments` takes the page's session and CSRF token, and the shell has only its admin token, so the service needs an admin route for attachments; (2) the chat screen would have to pick up an attachment id given in the address (for example `#/chat?attach=att-…`); (3) macOS asks for Screen Recording permission for the app, and for an ad-hoc signed app it is likely asked again after every new build (INFERRED from how macOS identifies ad-hoc signed apps; NOT VERIFIED).

### Needed outside the desktop (not changed here)

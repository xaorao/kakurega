# Canonical encoding for signed statements (experiment X6, decision D87)

## Target experience
A recipient verifies a capsule in a browser or a CLI with no trust in us. Two independent verifiers must compute identical bytes, so the encoding has to be unambiguous and simple enough that no implementation can drift.

## References
- Treeship `packages/core/src/canonical.rs` and `jcs.rs` (Apache-2.0, commit da7f8ac), read in full: its signing encoding is its own sorted-key JSON, not RFC 8785; a separate JCS module refuses floats and unsafe integers instead of guessing.
- RFC 8785 (JCS) and RFC 8259, `canonicalize` 2.1.0 (npm, the RFC author's JavaScript implementation).

## Approach
Kakurega signs RFC 8785 JCS over an integers-only profile: no floats, integers within +-(2^53-1), no `-0`, no duplicate keys (after escape decoding), no lone surrogates, no BOM, UTF-8 only, nesting depth at most 128. Anything else is rejected with a named code, never converted. Decimal quantities and large integers travel as strings. Two clean implementations were written from the grammar, not from each other: Rust (`crates/kk-evidence/src/canon.rs`) and JavaScript (`packages/canon-js/src/index.js`, no use of `JSON.parse`). Treeship's refusal rule is adopted as the profile; no Treeship code was copied.

## Quality criteria and result
- 26 accepted and 30 rejected shared vectors (`fixtures/canon/vectors.json`) pass in both implementations with identical error codes; accepted vectors were generated by the independent npm `canonicalize`.
- Differential test over 11,000 random documents (3 seeds, random keys including astral, private-use and control characters): Rust, JavaScript and npm `canonicalize` identical byte for byte, plus identical SHA-256.
- Treeship's published known-answer digest for `{"b":1,"a":2}` matches.

## Finding that shaped the design
On Node v25.5.0, `JSON.parse` returned the wrong key (backslash instead of tab) for a valid document, deterministically, also with `--jitless` (`tests/findings/node25-json-parse-key.mjs`). A verifier that parses with `JSON.parse` can therefore compute a different value than the signer. Our own strict parser avoids this, and the test oracle never uses `JSON.parse`.

## Not covered
Fuzzing beyond random structural documents (no mutation fuzzing of malformed input yet); WASM build of the Rust verifier (separate task); performance on large documents.

# Secret detection (shared crate `kk-secrets`)

## Why
Matrix F (`capability-matrix/F-desktop-docs-security-tooling.md`) measured Kakurega's own detection: three lists that disagreed (14 prefixes in memory, 8 markers in the importer, 5 in the release check). The importer, which decides what an agent may read, caught 20 of 45 secret-shaped files and withheld about 1.2 percent of ordinary source files for looking like secrets (`inputTokens += x`). The release check only compared exact tokens of 12 characters or more, so a short password, a fragment of a URL, or a base64, hex, URL-encoded or reversed copy of a withheld value passed.

## What changed
- One crate, `kk-secrets` (layer 1), used by the importer, memory and the release check.
- Provider formats (GitHub, AWS, Stripe, Slack, Google, Anthropic, OpenAI, GitLab, npm, PyPI, Hugging Face, DigitalOcean, Shopify, Twilio, Mailgun, SendGrid), private key blocks, signed tokens, URL passwords, NEAR and Solana keys, 64-hex keys after key-like names, recovery phrases. Provider layouts (prefix, alphabet, length) follow public token formats that the MIT-licensed gitleaks rule set also documents; the matcher, filters and wallet rules are our own code.
- Keyword assignments with false-positive filters: quote-aware values; unquoted code syntax, member paths, optional chaining, type annotations, paths, CamelCase and ENV_VAR names, test and placeholder markers, templated values, UUIDs and hash digests are not credentials; a credential needs digits or very high entropy; a long lowercase passphrase after a password keyword still counts.
- Decoded segments: base64 and hex segments are decoded with bounded depth (2), bytes (256 KiB) and segment count, and rescanned (Docker auth blobs, Basic headers, nested encodings). A decode bomb and 2 MB of noise finish inside a fixed budget (test sk03).
- Release egress: for each withheld file, whole tokens of 12+ characters, the values of assignments from 6 characters, and for values of 8+ characters their base64 (three spellings), hex, percent-encoded and reversed forms, plus the password and `user:password` part of credential URLs. Variable names are not values, so naming `PAYMENTS_API_KEY` is allowed. The shared detector also runs over every released file.

## Evidence
`cargo test -p kk-secrets` (corpus: 29 positives and 23 benign look-alikes), `cargo test -p kk-review --test release` rs08 (eight transformed or partial leaks rejected, a variable name accepted) and rs09 (provider secrets the old five markers missed). Measured false-positive rate of the generic scanner on real code trees from the local reference clones (`cargo run --release -p kk-secrets --example scan_tree DIR`): opencode/packages 8 of 8,359 text files (0.10 percent), openclaw/src 203 of 28,971 (0.7 percent), hermes-agent 246 of 22,069 (1.1 percent); the remaining hits were inspected and are almost all test fixtures and documentation holding example credentials, which are fail-closed (withheld) rather than leaked. The old importer withheld about 1.2 percent of opencode's real source for non-secrets.

## Limits (not verified or not done)
- The corpus tests in `crates/kk-secrets/tests/corpus.rs` are written by us. The independent comparison against gitleaks' own samples is described below; it was run once on the numbers given there and its samples are not kept in the repository.
- The recovery-phrase rule has no BIP-39 word list: it uses word shape, repeated words and common function words. Owed: embed the list.
- No PII detection yet (cards, IBAN, SSN, email, phone): matrix F rows P1 to P4.
- Base64 or hex fragments split across lines, other encodings (rot13, unicode escapes), and information leaked by paraphrase are not caught.
- `.kakuignore` (owner-declared withhold list) is not built (matrix F row S8).

### Independent benchmark (method, because it is the evidence)
gitleaks' own rule generator holds, for each rule, positive and negative sample strings. I ran its generator on a scratch copy (original clone untouched) with its `Validate` step changed to also write the samples out: 215 rules, 6,368 positive samples (each secret in all 28 wrappers), 342 negative samples. `tests/gitleaks_compare.rs` (ignored by default; set `KK_GITLEAKS_SAMPLES` to the file) feeds them through `kk_secrets::scan`. The samples contain fake secrets and are not committed.

| Stage | Positives found | Negatives flagged |
|---|---|---|
| Before this work | 4,178 of 6,368 (66%) | 80 of 342 |
| After | 6,172 of 6,368 (97%) | 78 of 342 |

Reading the 78: most are other gitleaks rules' true positives (a Cloudflare sample listed under the Meraki rule), placeholders gitleaks drops by entropy, or malformed Telegram samples that still sit next to the word `token`. These are not defects of ours; the number is not a false-positive rate.

The 196 positives still missed: client-id style rules for public identifiers (Asana, Discord, Plaid: EXCLUDED, a client id is not a secret and a digits-only value after a provider name is not distinguishable from any number), Lob test keys (the word `test` marks fixtures), the age key sample (all `Q`, a filler string, rejected on purpose by the placeholder rule; a realistic age key is found), and about 20 others (for example `s.` Vault tokens, which cannot be told from a member path `self.token`; the Facebook `appid|secret` pair).

### Real-code survey (false alarms and lost detections)
Old and new detector run over the same files of six MIT codebases (opencode, hermes-agent, goose, papermark, LibreChat, OpenHands): opencode 22 to 24, goose 19 to 18, papermark 0 to 0, LibreChat 438 to 366, OpenHands 60 to 33, hermes-agent 510 to 935. The hermes-agent increase is a documentation file with 241 Firebase download URLs carrying `token=<uuid>` (kept: such a URL is a capability link) and about 190 hard-coded fixture tokens inside test files.

### Corrections to earlier statements
- I wrote that gitleaks' percent decoder skips a `%XX` at the very end of a string. That was wrong: its condition `encIndex+2 < encLen` is exactly the last-three-bytes case. No weakness there.
- The comment on `identifier_shape` promised that UUIDs and hashes count when a keyword is next to them; the code did not do it. Fixed.

### Defects found in the existing code while doing this
- Reading the key name around a keyword walked the entire surrounding run of letters: a 4.5 MB base64 blob took 2.1 s because every incidental `key` re-walked it. Now bounded to 80 characters (0.34 s); test cx12.
- Hit spans for a quoted value started on the opening quote and stopped one character short of the secret. No caller used spans yet, so nothing leaked, but redaction by span would have left the last character. Now exact; test cx13.

### Evidence
`cargo test -p kk-secrets`: corpus 6, formats 5, context 15, pii 6; `node --test` in `apps/extension` 14. Mutation checks: 40 safeguards removed one at a time over four rounds, each now fails at least one test (the rounds also exposed gaps in my own tests, such as a placeholder-word test whose body the alphabet cut short, which were fixed and rerun). The detector crate is built optimised in the dev and test profiles (workspace `Cargo.toml`) so the bounded-time tests measure the algorithm.

### Remaining limits
- The benchmark is gitleaks' own samples: it favours gitleaks' idea of a secret and its 28 wrappers. It says nothing about secrets written in prose.
- The format lengths come from gitleaks' patterns, which are not anchored at the end; where a real token is longer than the pattern's minimum we require the exact documented length.
- Flutterwave live keys and other providers whose live layout gitleaks does not list are NOT VERIFIED and not added.
- `scan` still has no notion of file type or language.
- A password written as dashed lowercase words with no digit (`correct-horse-battery-staple`) is not flagged: the older readable-identifier rule drops it on purpose, and I kept that precision choice. The same words with a number are flagged under a password name.
- Test fixtures that look like real tokens (`ghp_` followed by 36 plausible characters inside a test file) are flagged: nothing distinguishes a fixture from a leaked token except its path, which `scan` does not see.

## Owner allowlist for the personal-data notice (ledger F-P3)
- Reference read in full: Privateer `src/config/piiAllow.ts` (118 lines) and `tests/piiAllow.test.ts` (79 lines), commit 181a988, MIT. It keeps `privacy.piiAllow` in the operator's config file (exact values, `*` globs, `@domain`, IPv4 blocks), re-reads it live, treats a malformed file as "no entries" so detection errs toward more, refuses a bare `*`, and adds or removes idempotently while keeping the rest of the config. Its reason: under its "no quarter" mode a false positive becomes a silent rewrite the model reads, so the person needs a way to say "this is not personal data".
- Taken and changed: the same entry forms for the kinds we detect (email, card, IBAN, PAN, Aadhaar, SSN, phone); no IPv4 blocks (we detect no IP addresses). Ours is stricter on what an entry may be (at least four letters or digits of its own, so `*@*` and `@com` are refused; a domain entry must be a real domain; no control characters; 200 characters; at most 200 entries) and a stored entry that fails the check is ignored, so a damaged list reports more, never less. Matching is anchored at both ends, ignores case, and for numbers ignores spaces and dashes; a domain entry matches the domain and its subdomains only (not `notacme.com`, not `acme.com.evil.org`); wildcard matching is iterative so a hostile pattern cannot blow up. It lives in the encrypted store (the values are real addresses), not a config file, and is reached only by the owner's session (`GET`/`POST /api/pii-allow`, `/pii` in the terminal).
- Not silent: the release view reports `personal_data_allowed` and adds a line to "This release does not establish" naming how many values were left out because they match the owner's list. The log records only the number of entries, never a value. The allowlist changes only the notice: nothing is sent or withheld differently (the notice never blocked anything).
- Excluded on purpose: Privateer's silent auto-redaction ("no quarter"), already EXCLUDED in matrix F as P4.
- Evidence: kk-secrets pa01–pa05 (11 tests incl. hostile patterns), kk-service sv110 (auth, refusals, counted left-out values, removal, cap, log, restart), kk-tui tu62; 13 mutants caught (two needed new assertions).
- Web editor (added later, same ledger row): Settings, under Privacy, has "Values that are not personal data": the list, an add box, a remove button per value, the service's reason when an entry is refused (for example `*`), and a note when adding or removing changed nothing. It uses the same API as the terminal, so the same checks apply. Evidence: browser checks (400: found by a word people use, added and listed, a match-everything pattern refused with the service's text and nothing added, the same value again changes nothing, still there after a reload, removed, accessibility scan) with 6 mutants caught after one check was tightened (the first version did not check the refusal's wording). Not verified: that the notice itself changes on a real review after an edit in the web (the service test sv110 covers it through the API).
- Not covered: the capsule itself does not carry the list (the notice is an owner-side view), an owner-set list applying to chat attachments (a different detector), a cap on how often it can be changed.

## Planted-canary attack grid (ledger F-I4, F-I5)
- Read as the reference idea: a grid of projects against attack goals, graded deterministically by the presence of a planted value (not by judging text). Built our own, with values that are new in every run.
- Built: `j13` in `crates/kk-review/tests/job.rs` (runs in the Linux VM with the other job tests, so it is in the `lima` gate step). Per run it plants four fresh random secrets in each of two projects (Python, JavaScript): one appended to `.env` (secret by name), a key in `deploy/id_rsa` (by name), a live-looking key inside an ordinary source file (by content only) and a note under a path in `.kakuignore` (by the owner's list). Five attacks, each driven by a scripted hostile model: read each file by path; path tricks (`./`, `..`, absolute, wrong case, doubled slash, backslash); tools that must not exist (shell, fetch, email); findings that cite the withheld files so their lines would be quoted; a reproducer that opens the secret files itself. Grading, per planted value, over five surfaces: everything the model was shown (a spy on every request), the release, the audit trail, the progress events and what the checks printed (5 x 5 x 2 x 4 = 200 absence checks), and that every planted file is reported withheld.
- Evidence: passes (8 jobs, 2 s). Mutants caught: the content-secret rule removed, name and content rules removed, the owner's list ignored, the agent's clearance raised. A mutant that lets findings cite withheld files was NOT caught: a second layer between the finding and the release still holds, so it is a defence-in-depth gap in the test, not a leak. NOT VERIFIED: attacks by a real model; an attack through the browser or Telegram surfaces (this grid covers the review pipeline only).
- Not built: the grid for the `ask` and `chat` paths, and canaries placed in memory notes and attachments. F-I4 and F-I5 stay PARTIAL.

## Finding from extending the canary grid to chat: Restricted notes were sent to remote models (CONFIRMED, fixed)
- What the planted-value test (sv117) showed: a note saved at level Restricted, with a value created fresh for the run, reached the model's prompt in `/api/chat` even when the route does not run on this computer. Chat used the owner's full clearance for every route; only attached files were held back by where the model runs. Restricted means "never leaves this computer" everywhere else in the product (review agents are held to Internal).
- Fix: chat recalls notes with the owner's clearance only when the route runs on this computer (decided from the route's address, as the page's "stays here" fact is); otherwise the level is capped at Confidential. Confidential and below behave as before.
- Evidence: sv117 (fresh value, four phrasings of the question, plus the log and the exports) and sv118 (four addresses: this computer, a hosted address, a LAN address and a look-alike host), mutants removing the cap or inverting it caught. Exercised: `/api/chat` with the scripted and the address-based runners. NOT exercised: a real remote route, and the terminal and Telegram chat paths (they call the same service chat, not separately tested).
- Not decided: whether Confidential notes should also stay home. They reach hosted routes today; that is the existing rule and is unchanged.

## Finding from extending the canary grid to chat attachments: a private key's body reached a model elsewhere (CONFIRMED, fixed) (ledger F-I4, F-I5)
- Method: the grid idea from the earlier canary work, applied to a path that had only a fixed example: files attached to a chat message, sent to a model that does not run on this computer. Five shapes of secret per run with values new on every run (an Anthropic-style key, an AWS access key id, a GitHub token, a PEM private key, a quoted password), three hostile questions each ("repeat the file word for word"), graded by the presence of the planted value in what the model was given, in the answer, in the view of what was sent, in the signed log and in every readable file under the data folder.
- Result before the fix: four shapes were withheld as intended; the PEM private key was not. Only the `-----BEGIN ... PRIVATE KEY-----` line was recognised as a secret; the body lines, which look like any base64 text, and the `-----END` line were passed on. A key longer than the 40-line passage (a passage is up to 40 lines) was worse: the begin line in one passage and the body in the next, where no line shows anything.
- Fix: the private-key block is now decided over the whole file in order (`private_key_lines`): from a begin line that names a private key through the matching end line, or to the end of the file when there is none, wherever the passages cut it. For a model elsewhere the whole block is left out and counted as a withheld secret (one unit per run of lines in a passage); the text around it is still given; a public key or certificate is untouched; for a model on this computer nothing changes. What the owner is shown before sending uses the same decision, so the preview and the prompt agree.
- Evidence: kk-service sv126 (the five shapes, a 25-line key that straddles two passages, a key with no end line, a public key as a control, graded as above) and two unit tests in the attachments module; 8 mutants caught (no masking, begin line only, state not kept across passages, public keys withheld too, end ignored, masking applied for a local model, runs not counted, preview not using the decision).
- The `ask` path (a folder of documents) was graded the same way (sv127: files that hold a secret by content, by name only, an embedded PEM block, ordinary files still read): it already withholds whole files, not lines, so this defect could not occur there; 3 mutants caught across three repeated runs each, after the first version of the test could not tell the name check from the content check (a random value is sometimes flagged by content and sometimes not, so the name-only files were added).
- Not covered: web pages and search results as a source of secrets, a secret split across two lines of ordinary text, encoded forms of a key inside a file. F-I4 and F-I5 stay PARTIAL.

## Sweeping random secrets through the detector: three ways a real secret was taken for something else (CONFIRMED, fixed) (ledger F-I4)
- Method: 21 shapes of secret (Stripe, Slack, Google, SendGrid, npm, PyPI, JWT, database and basic-auth URLs, JSON private key, bearer header, YAML and env assignments, AWS secret, GitHub fine-grained, GitLab, Azure connection string, Twilio, OpenAI, Mailgun, a password in a sentence) and 10 ordinary look-alikes (git hash, UUID, SHA-256 digest, base64 image, prose, version strings, colours, paths, URLs) with values that are new on every run, then a sweep of 1,000 to 4,000 random values per shape to measure the miss rate. The look-alike URL with an `example` host is excluded by design and not counted as a miss.
- Found 1: `password: YqSYcZaiM9aIjsnGIS5X` (mixed case, one or two digits) was let through in 1,292 of 4,000 random values (32%). The rule that keeps CamelCase names such as `MyPasswordField` from being read as secrets treated any letters-and-at-most-two-digits value with one lower-to-upper step as a name. Fix: a name must be made of words (each capital starts a word of two letters or more, at least two words, at most two digits at the end, a numeric type name such as `AtomicU64` counts as a word). Now 46 of 4,000 are missed, all of them values made of letters only with no digit, which the existing entropy line handles at 20 characters or more (documented, not changed: lowering it flagged identifiers such as `CredentialAccountStatus` in 43 more places in one corpus).
- Found 2: an AWS-style secret access key (the alphabet includes `/` and `+`) was taken for a file path when it started with `/` or held two slashes: 90 of 999 (9%). Fix: a value is a path only if its first one or two segments read as names (`/home/deploy/...`, `/srv/Backup20240131/...`); a long value with the variety of a random key, mixed case and a digit, no dot, is judged as a key unless it begins like a path. Now 0 of 999.
- Found 3: a random token that spells `test`, `mock`, `fake` or `demo` by chance (about one in a thousand 32-character tokens) was dropped as a fixture. Fix: those four short words no longer excuse a value of 24 or more characters shaped like a token (mixed case, a digit, no dot, entropy 4.2 or more); the words that say what a value is (`example`, `placeholder`, `dummy`, `redacted`, `sample`, `changeme`, `lorem`, `default`, `xxxx`) always excuse it, so the AWS documentation sample key stays a sample.
- Precision on real text (VERIFIED, scratch scan of every line of 25,710 files from three AI-agent projects, before and after on the same files): hermes-agent 19,136 files 601 flagged lines both times, goose 1,977 files 23 both times, ironclaw 4,597 files 189 before and 190 after. The one new line is `"nextPageToken": "CiAKGjBpNDd2Nm"` in a Google Calendar fixture, an opaque token under a name that says token. A first version of fix 1 that also lowered the entropy line added 43 false alarms in ironclaw (type names) and was not kept.
- Evidence: `crates/kk-secrets/tests/secret_grid.rs` sg01 to sg08 (the grid with fresh values, a 4,500-value sweep with a digit that may miss at most three, names of words that must stay names, AWS-style keys with slashes, marker words in tokens and in fixtures, and the edges of each rule); 13 mutants of the changed rules caught after controls were added for the ones that first survived.
- Not changed, recorded: letters-only values of 20 characters or more after a password name are still missed about one time in a hundred; a password written as a sentence of words is not distinguishable from prose; `example` hosts in URLs are excused on purpose.

## Sweeping the personal-data notice: two ways a real number was not counted (CONFIRMED, fixed) (ledger F-P1, F-P3 area)
- Method: 1,200 payment-card numbers with a correct Luhn digit in six layouts (plain, spaced, dashed, inside JSON, an American Express grouping, inside a sentence), emails, phone numbers in eight layouts, US social security numbers, PANs and IBANs, against look-alikes (16 digits that fail the checksum, timestamps, ticket ids, version strings, wrong check digits). Cards: all found, no false alarm. Misses: an IBAN printed in groups of four as on a statement (`GB82 WEST 1234 5698 7654 32`, only the compact form was found) and a US phone number with the area code in brackets (`(415) 555-2671`, `+1 (415) 555-2671`).
- Fix: an IBAN is now also read as groups of up to four letters and digits separated by single spaces (the first group exactly four, the groups together a valid IBAN by the mod-97 check, a group that runs on into a lower-case word breaks it); a three-digit area code in brackets followed by a space is read as the first group of a phone number, which then has to pass the same grouping check as before.
- Precision on real text (VERIFIED, scratch scan of every line of the same three projects, before and after): goose and ironclaw unchanged; hermes-agent 13 more phone numbers (337 to 350), all of them real-looking US numbers in test data such as `(555) 867-5309` and `+1 (555) 765-4321`; no IBAN found in any file before or after.
- Evidence: `crates/kk-secrets/tests/pii.rs` pi20 (four published IBANs, printed and compact, two in a line, seven that must not match, a following phone number still read) and pi21 (four bracket layouts, eight that must not match); 11 mutants run, 6 caught plus 1 more after a control was added, and 4 equivalent (a minimum group count and a first-group length that the IBAN check already enforces, a length bound that cannot change which prefix is valid, and two bracket details the grouping check repeats).
- Not changed, recorded: a bare ten-digit mobile number (`9876543210`) is still not claimed, since ids and timestamps look the same; an email whose local part is in quotes is not found. The notice does not block anything, so a miss here costs a missing line in the notice, not a leak.

## Links and the owner's withhold list through the `ask` path and a review (ledger F-I4, F-S8)
- Method: the same fresh-value grading, on a folder holding a link to a file outside every allowed folder (value new in each run), a link to a folder outside, a relative link to `/etc/hosts`, and a file the owner listed in `.kakuignore`. Graded by the planted value in what the model was given, in the answer, and in the review's result.
- Result: nothing reached the model; the outside value never appeared. The importer holds this two ways: it never follows a link (`symbolic link (never followed)`) and reads each entry with `symlink_metadata`, so a link is neither a file nor a folder to it. Removing the first layer alone did not fail the test (the second layer still held); removing both let the outside file in and the test failed, so it guards the property and not one line.
- Evidence: kk-service sv128 (links to a file and a folder, a relative link, a `.kakuignore` entry with an unlisted twin of the same form that must still be read, an upload name with `..`, a review of the same folder); 3 mutants run, 2 caught (both link layers removed; the owner's list ignored) and 1 equivalent (the first layer alone, because the second still holds). No product change. While writing it, two assertions I meant to add had silently not been applied by my own edit script; the mutant for the owner's list survived and exposed that, which is why every new assertion is now checked against a mutant before it counts.

## Random secrets taken for names or fixtures (CONFIRMED by a failing gate, fixed) (ledger F-S3)
- How it was found: the gate's own random-secret grid (`sg01`) failed once with "yaml password not flagged". It draws new values from the clock each run, so one run in a very few thousand misses. The test reported only the shape, not the value, so it is now printed.
- Method: 200,000 to 1,000,000 deterministic random values (16 to 32 characters, mixed case with a final digit, or capitals and digits only) after `password:` and `totp_secret:`; each miss sorted by which rule rejected it, read from the code (`literal_credential`, `camel_identifier`, `placeholder`).
- Findings (VERIFIED by the sweeps, before the fix): about 0.085% of mixed-case values were taken for a CamelCase name, because a random string cut at its capitals gives pieces such as `Bk` and `Cq` that count as two-letter words; about 0.02% had the letters of `todo`, `mock`, `fake`, `xxxx` and similar inside them by chance and were treated as fixtures; and **72% (144,902 of 200,000) of random capitals-and-digits values of 16 or more characters, the shape of a base32 or hexadecimal secret such as a TOTP seed (`JBSWY3DPEHPK3PXP`), were taken for environment variable names and let through.**
- Fix, measured against about 33,000 real CamelCase identifiers and 3,300 real constant names read from this repository and its dependencies: a CamelCase name must have a vowel in every word, or be a known consonant-only word (`Http`, `Jsx`, `Fs`, `Ctx` and about forty others); in a value that mixes cases, a four-letter marker word (`test`, `mock`, `fake`, `demo`, `todo`, `none`, `null`, `true`, `xxxx`) counts only when it is case-uniform and starts a word (`TestKey`, `mockSecret9`, `Testing`), not when it is spelt across a case change (`moCk`, `EtODo`); a value of capitals, digits and underscores is a variable name only if it has an underscore, is shorter than 16 characters, or has no digits.
- Result (VERIFIED): mixed-case values let through 170 per 200,000 before, 19 after; capitals-and-digits 144,902 before, 25 after. 99.4% of the real identifiers stay names. The 8 real constants that are no longer treated as names are IBAN samples, alphabets and an example key, which are values.
- Residual, recorded and not hidden: about 0.009% of mixed-case values are cut into pieces that each have a vowel and still read as a name; the values left in the capitals sweep contain a marker word spelt in capitals. Two further rules were measured and rejected: a limit of four consonants in a row (cuts the residual from 85 to 52 per million but withholds 0.4% of real names) and treating `y` as a vowel only in longer words (85 to 71, 0.7% of real names). Telling these apart fully would take a dictionary.
- One earlier pin was changed on purpose: `sg07` held that `Test` glued into the middle of random letters after a capital stays a fixture; that is the chance pattern behind the misses, so it is now flagged, and the same marker at the start of a word still is a fixture.
- Evidence: `crates/kk-secrets/tests/secret_grid.rs` sg09 (eight formerly missed values, and the two sweeps with their limits), sg10 (14 real names, 6 variable names, 5 fixtures stay as they were), sg07 (changed pin and its word-start counterpart). sg09 and sg07 fail on the old code. 17 mutants caught; the first rounds of mutants showed two weak tests (names without digits cannot test the abbreviation list, no value contained `XXxx`), which were strengthened. The whole workspace test suite passes.
- Not covered: other key names than `password`, `totp_secret` (the grid and `sg02` already cover several), values longer than 32 characters or with symbols in this sweep, and lower-case-only random values (their marker rule is unchanged).

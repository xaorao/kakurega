# Linux worker sandbox (experiment X2, tests R01-R21, R30-R35, SC01-SC07, FF01)

## Target experience
Whatever a worker is made of (a model-driven agent, a parser, a script it wrote itself), it can read only what it was handed, can talk to nothing but the broker, and cannot use up the machine. The person is told if the machine cannot give that guarantee.

## References
Bubblewrap 0.11.1 (the sandbox Codex also uses); Codex's launch sequence and MXC's bubblewrap backend (surveyed in earlier experiments E1-E17); `nearai-red-sandbox` is still to be read in full (not done). **Codex** (`openai/codex` commit f2b94ef, Apache-2.0): `codex-rs/linux-sandbox/src/seccomp.rs` read in full (306 lines) and `bwrap.rs` lines 225-415 of 1537 (the flag list and mount order); NOT READ: `linux_run_main.rs`, the proxy files, the WSL handling. Its seccomp filter is where the missing layer below was found. Earlier attack experiments on this VM are in `private-ai/specs/experiments/`.

## Approach (`kk-sandbox`)
`bwrap` with `--unshare-all --unshare-user --disable-userns`, `--die-with-parent`, `--new-session`, `--clearenv`, `--cap-drop ALL`, a private `/proc`, `/dev` and `/tmp`, and an allowlist filesystem: read-only `/usr` plus the binds the kernel names. No host paths are visible. Limits come from a systemd user scope (`TasksMax`, `MemoryMax`, `MemorySwapMax=0`) plus `prlimit` for CPU, file size, open files and core size; stdout and stderr are capped; a wall-clock watchdog stops the scope. Before running any worker the launcher runs a probe worker under the same profile and refuses to start if the probe can reach a host listener over IPv4 or IPv6, resolve DNS, read a planted secret, create a nested user namespace, or see more than a handful of processes. The broker channel will be a unix socket in a per-worker directory bound into the sandbox (not an inherited descriptor, because the crate forbids `unsafe`).

## Found by a hostile test: a hung worker was never stopped through the Lima route (VERIFIED, fixed)
- **The defect:** from the Mac, the wall-clock limit killed only the local `limactl` client. The sandboxed process inside the VM kept running, and the caller then waited for ever for the output pipe, which the still-running `ssh` held open. A test with an idle hang (a `setInterval` test file; a busy loop is stopped earlier by the CPU limit, which is why earlier hostile tests did not show it) sat for 20 minutes against a 60 second limit. The same gap applied to the broker worker's line-serving path.
- **The fix:** the host now chooses the systemd scope name (`kk-worker-<digits>-<digits>`, checked by `valid_unit_name` on the VM side before it is used), sends it in the wire spec, and on a timeout or an oversized line runs `systemctl --user stop` for that scope inside the VM. Reading the output pipes is bounded (10 s) so a pipe that something still holds can never hang the caller.
- **Tests:** `w01`, `w02` (names, hostile forms), `l03` in Lima: a sleeping worker with a 4 s limit returns `TimedOut` in about 6 s with its output, and no process (found by a per-run marker) or running scope is left in the VM. Mutations caught: scope not stopped, host unit name ignored in the VM, reader wait removed, and three on the name check.
- **Cleanup facts:** killed or limit-stopped scopes leave `failed` scope records (108 had accumulated from earlier limit tests); `systemctl --user reset-failed` clears them. Mutant runs that skip the stop leave 300-second sleepers behind, which contaminated a later baseline run once; tests now use a unique marker per run.

## Added after reading Codex: a system-call filter (VERIFIED_BY_RUN, same VM, aarch64)
- **The hole, reproduced before fixing:** inside the exact profile above, Python could create an `AF_VSOCK` socket and connect to the host (CID 2); the host answered with a connection reset, so the connection crossed the VM boundary. A VM socket is not a network-namespace object, so `--unshare-all` does not cover it. Codex's comment says the same, and adds that `io_uring` can open sockets without a `socket` call.
- **The filter:** `bwrap --seccomp`, a classic-BPF program written in `crates/kk-sandbox/src/seccomp.rs` (no new dependency, no `unsafe`). It returns `EPERM` for `socket` and `socketpair` with any family except `AF_UNIX`, for `io_uring_setup/enter/register`, `ptrace`, `process_vm_readv` and `process_vm_writev`; it kills the process for any other architecture and for the x86-64 x32 ABI. One program carries both aarch64 and x86-64 tables, so the macOS-host-to-Linux-VM path needs no architecture guess. The numbers come from the `libc` crate's per-architecture files and the Linux headers in the VM (read, not recalled), are typed into a test as literals (sc07), and the build architecture's are also compared with `libc` in the VM (sc06).
- **Delivery:** the program is written to an owner-only file in `XDG_RUNTIME_DIR`; a three-line `sh` wrapper opens it as descriptor 9, deletes it, then runs `systemd-run ... prlimit ... bwrap --seccomp 9`. The descriptor was tested through that whole chain by hand first. If the file cannot be written, nothing runs (ff01). The Lima path ends in the same function, so both transports are covered.
- **Checked on the real kernel:** vsock, inet, inet6, netlink and packet sockets are refused; `AF_UNIX` and socketpairs work; `io_uring_setup` and `ptrace` are refused (r30). With the filter off, the same code reaches the host over vsock (r31), which proves the test can see the hole. Ordinary Python (threads, fork, subprocess, multiprocessing) and Node (child process, worker thread, fs, timers) run normally under it (r33, r34). The launcher's self-check now probes the filter, with positive controls so an over-tight filter cannot pass (r32).
- **Emulator tests (any machine):** a small BPF interpreter checks every decision for both architectures, the family compare on the low 32 bits, foreign architectures and the x32 numbers (sc01-sc07).
- **Mutations:** 11 applied, all caught (filter not attached, any family allowed, io_uring not denied on x86-64, x32 not killed, unknown architecture allowed, a wrong aarch64 number, filter file kept, the network weakening keeping the filter, the probe forgetting vsock, failing open when the file cannot be written, socketpair unchecked).
- **Checked and not needed:** the kernel keyring (`keyctl`) is not reachable from the sandbox, tested with a secret added to the user keyring outside ("required key not available" inside), so no keyctl rule was added.
- **Test fixes this forced:** the old probes created a socket outside a `try`, so a refused socket crashed them (the self-check failed closed, which is correct); and the old UDP assertion passed only through an `||` clause that happened to be true. It now drains the control run's datagram and requires that nothing arrives from the sandbox.

## Results (VERIFIED_BY_RUN in the Lima VM `kak`: Ubuntu 26.04, kernel 7.0, bubblewrap 0.11.1; `scripts/test-linux`)
- R01-R06: control run reaches the host listener (5 connections) and sends UDP; sandboxed run: TCP v4, v6, v4-mapped, raw sockets, DNS, curl, bash `/dev/tcp` and proxy-environment attempts all blocked, and the host listener sees no connection.
- R09, R11, R12: direct path, home-directory secret, `/etc/shadow`, `/proc/1/root`, a symlink to the secret, a hard link, `..` traversal all fail; `/home` is empty; only descriptors 0-3 exist in the worker.
- R13, R15: a host process cannot be killed or seen; nested user namespace, network namespace, `sudo`, `mount`, `chroot` fail; effective capabilities are zero.
- R18: a fork bomb stops at the process cap, a memory hog is stopped at the cgroup limit, a CPU spin is stopped, a sleeping worker is killed at the wall limit, a disk filler is stopped by the file-size limit, an output flood is capped.
- R21: the launcher's own probes pass on the real profile and report failures when the profile is weakened (shared network; nested user namespaces allowed).
- The parent's environment variables (including a fake API key) never reach the worker.
- Mutation checks, applied and verified to have rebuilt: removing `--unshare-all` fails 3 tests; always sharing the network fails 2; binding the whole host root read-only fails the filesystem test. Removing `--cap-drop ALL` is not detected, because an unprivileged sandbox already has no effective capabilities (an equivalent mutant; the flag stays as defence in depth).

## Findings
- `--unshare-all` alone does not unshare the user namespace; `--disable-userns` fails with "requires --unshare-user" until `--unshare-user` is given explicitly.
- `RLIMIT_NPROC` counts every process of the user, so it cannot cap a single sandbox and starved the launcher when tests ran in parallel. Per-sandbox process and memory caps need cgroups (systemd user scopes). A host without a systemd user session is reported as unsupported rather than silently run without caps.
- The VM mounts the repository read-only and its view of changed files can lag by a few seconds; a mutation test run too soon after an edit silently tested the old code. Mutation runs now wait and confirm a rebuild.
- The exhaustion test (r18) failed twice more on the new code, both within the first few runs after a rebuild: once in the memory half (killed by SIGTERM instead of SIGKILL) and once after 0.07 s (its message was not captured). Afterwards: 0 failures in 31 runs on the new code (14 of r18 alone, 12 of the whole suite, 5 more) and 0 in 37 on the unmodified commit (25 and 12). That is consistent with the earlier sighting being tied to a rebuild, not to the filter, but it does not prove it: the cause is still unknown: OPEN. One run of the exhaustion test failed once in about 21 runs, the first run after a rebuild, before diagnostics were added; it did not recur in 12 isolated and 8 full runs. Cause unknown: OPEN. Diagnostics now print exit status and output on failure.

## Out-of-memory kills and the intermittent r18 failure (found and fixed)
- **Symptom.** `r18_resource_exhaustion_is_bounded` failed now and then with `memory not bounded: exit Signal(15)`, mostly on runs through `cargo test` and in clusters (twice in a row in the full VM suite). It had been recorded as an unexplained flake.
- **Cause (VERIFIED from the VM journal on a failing run).** The memory limit always worked: the kernel's cgroup out-of-memory killer killed the Python process at 400 MB (`Memory cgroup out of memory: Killed process ... python3`, `Failed with result 'oom-kill'`). What varied was what the host then saw. systemd's default `OOMPolicy=stop` also stops the whole scope with SIGTERM after an out-of-memory kill; when that SIGTERM reached the sandbox's head process before it had reported the child's death, the result was `Signal(15)` instead of the accepted `Signal(9)` or `Code(137)`.
- **Fix.** The scope is created with `OOMPolicy=continue` (`scope_args`), so the kernel kill is the only event and the sandbox reports it itself. Test `w_scope_limits_are_set_and_an_out_of_memory_kill_does_not_make_systemd_stop_the_whole_scope` (fails without the setting).
- **Evidence and its limit.** In the VM, 30 runs of r18 through `cargo test` passed with the fix; 30 runs without it gave 1 failure. That difference alone is NOT statistically conclusive (a rare race); the conclusion rests on the journal showing the mechanism. After the fix the full VM suite passed twice in a row.
- **Process note.** Commit 05bda55 (Release tab) was made while this suite was failing, because the commit step did not check the VM exit code. That change is web-only and unrelated; the gate commands now stop on any non-zero exit before committing.

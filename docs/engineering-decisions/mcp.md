
## Resources and a prompt (ledger D-D24, D-D25, D-D26)
- Reference: the official Rust SDK (`rmcp`, Apache-2.0, `crates/rmcp/src/model/resource.rs` read in full, `prompt.rs` core types read) for the exact wire shapes: `Resource` (uri, name, title, description, mimeType), `ResourceTemplate` (uriTemplate), `ResourceContents` (uri, mimeType, text), `Prompt` (name, title, description, arguments with required), `PromptMessage` (role, content). The server itself is hand-written already (decision in this file); only the shapes were taken. NOT READ: the SDK's server handler traits and the spec pages for resource subscriptions.
- Decision: BUILD. A resource or prompt is a second door to code the tools already guard, so it gets no logic of its own: a read runs the same tool through the same `call` (lease, output-schema check, audit under the tool's name). Listing and reading both require the backing tool to be visible under `--read-only` and `--allow`.
- Beats the usual implementation: the common MCP servers list resources unconditionally. Here an address that is not exactly a listed shape never leaves the process (no path, no query, no encoding tricks), a prompt is hidden unless every tool it uses is allowed, and prompt values are inserted as quoted text and refused if they contain control characters.
- Evidence: mc35–mc41 in kk-cli (listing, capabilities, read equals tool, 17 hostile addresses, 7 argument shapes, gating under allow/read-only, audit names, service down), live in `mcp_live.py` (51/51), 19 mutants all caught, `scripts/docs_check.py` now also compares the document's resources and prompts with the server's.
- Not covered: resource subscriptions (not offered, advertised as `subscribe: false`); clients other than the scripted ones (no real MCP client was driven); prompt text quality against a real model (needs a model).

## Installing the server into a client (ledger D-D38)
- Client formats VERIFIED from the vendors' pages, fetched through the reader proxy: Claude Code `claude mcp add --transport stdio <name> -- <command> [args...]` (https://code.claude.com/docs/en/mcp, "stdio servers"); Claude Desktop `claude_desktop_config.json` with `mcpServers` entries of `command` and `args`, macOS `~/Library/Application Support/Claude/` (https://modelcontextprotocol.io/quickstart/user; the file also exists on this Mac without any server entry); Cursor `mcp.json` with `type: "stdio"`, `command`, `args`, project file `.cursor/mcp.json` (https://cursor.com/docs/context/mcp). NOT VERIFIED: Cursor's global file path (not on the fetched page), and whether the proxy dropped it from a code block.
- Hermes `mcp_security.py` (read earlier, trace row) blocks client config entries that match attack indicators at save and at spawn. That guards a tool that writes configs. Kakurega does not write them, which removes the attack class: a planted config is the owner's to place, and the printed text names the binary by full path and digest so a swapped file is visible.
- Decision: BUILD `kaku mcp install --client NAME --print`. `--print` is required so a script cannot believe a file was changed; the command has no write mode. No token is ever part of the text: the server resolves it from the data folder at start, and the test plants a token in `admin.json` and in the environment and checks neither appears.
- Beats the docs-snippet approach: the path is the real binary, the limits are carried (and an unknown flag or tool name is refused, so a typo cannot print a config that widens access), shell quoting is checked against a real `sh` for 14 awkward paths including `$(...)`, backticks, quotes and newlines, and the printed command is run to prove it starts a server with the same limits.
- Evidence: kk-cli `mi01`–`mi08`, live `mcp_live.py` 52/52, 14 mutants all caught; a debug-build speed fix (`sha2` optimised in dev and test profiles) because hashing an 80 MB debug binary took 2 s per call.
- Not covered: Windows (the Claude Code line is refused there by code that no test runs; the JSON form is unexercised on Windows), a real Claude Desktop or Cursor loading the printed block, quoting for fish or PowerShell.

## Catalog digest and report links (ledger D-D20, D-D23)
- Reference: the matrix rows (spec wants a deterministic tool order and links that are not guaranteed to be listed; clients that pin definitions re-prompt on change). NOT READ: the current spec text for `_meta` keys beyond the matrix summary; the key names are ours (`com.kakurega/...`, reverse-domain as the spec asks for custom meta).
- D20: digest = SHA-256 of the tool list as written on the wire. `initialize` and `tools/list` carry the full-catalog digest, `tools/list` also the digest of what that connection was shown; `kaku mcp --print-catalog-digest` prints it (and refuses any other option). The golden file still guards the source; the digest lets a client detect a swapped binary. It is not a signature: it proves the list is unchanged, not who built it.
- D23: the full report of `verify_capsule` and `verify_log` is a `resource_link` (`kakurega://verification/<16 hex>`), never embedded content; reading it goes through `resources/read`, the same gated door as the tool. Eight newest per connection, 64 KiB each, same report same address. A failed call has no link; a log that fails verification is still a report and has one.
- Evidence: kk-cli mc42 (stable across starts, listed digest differs under `--read-only`), mc43 (link, read equals structured content, never `type: resource`, 6 odd addresses, eviction, no cross-connection reads), mc44 (twelve repeats do not push out another report; reads are audited as the tool); live script checks the digest. 10 mutants caught after two tests were added; the id-format pre-check was removed as dead code (lookup by exact match already refuses anything else).
- Not covered: a real MCP client rendering the link; the `sees(tool)` guard on reads is defence in depth that no test can reach on one connection.

## Trace context in the signed log (ledger D-D14)
- Reference: the W3C Trace Context `traceparent` format (specification) as clients put it in `params._meta`. No local MCP client source was found that sets it (the only hits in the local clones are promptfoo tests); the key's presence in `_meta` is OBSERVED in the matrix, not read by me in a client here, so the claim that real clients send it is NOT VERIFIED.
- Behaviour: `kaku mcp` forwards `params._meta.traceparent` (a string of at most 64 characters) with its record of a tool call; the service keeps it in the signed `mcp.call` entry only if it is a well-formed version-00 `traceparent` (lowercase hex ids that are not all zero) and drops it silently otherwise. The call is recorded either way. It is a client-chosen label: it decides nothing and is never used for access. The 120-calls-a-minute limit still applies.
- Evidence: kk-service sv103 (a good id appears in exactly one record; nine malformed ones, including an instruction as text, never reach the log; every call is recorded); kk-cli mc45 (extraction only from `_meta.traceparent`, strings only, length bound). 11 mutants caught.
- Not covered: `tracestate` and `baggage` (not stored, by choice: free-form client data); a live client sending a real trace.

## Change feed: `review_events` (ledger D-D27, D-D09)
- Reference: the matrix rows (a cursor feed any client can poll; MCP progress and resource subscriptions) and the earlier reading recorded in the trace for rmcp's serve loop and OpenCode's event client (`client/src/solid/connection.ts`, `shared-events.ts`, FULL, in the trace). Not re-read for this step. Decision: a cursor feed first, because it works with every client, whereas progress notifications and subscriptions depend on what the client supports and could not be tested against a real client here.
- Behaviour: every review event now has a position (`seq`) in one order across all reviews, kept across restarts (the counter continues from the stored events; the "service stopped" event of an interrupted review is added after it, so a client's remembered position never skips it). `GET /admin/events?after=N&limit=M` and the read-only MCP tool `review_events {after, limit}` return `{events: [{seq, review, stage, at}], next, latest, reset}` in order, at most 100 at a time. Only the stage name is returned, never the detail (which can name a file or a recipient). A position newer than any that exists (the service restored from an older copy) answers `reset: true`. Events stored before positions existed (position 0) are not listed. The tool needs no lease and is visible in read-only mode; its integer arguments are checked against the schema's minimum and maximum before anything is sent (a new `integer` type in the argument checker).
- Evidence: kk-service sv105 (stage-only records, strictly increasing, pages resume with no gap or repeat, a new review's events come after the cursor, a future position resets, the limit is clamped, junk is refused, three reviews run at once and are paged one event at a time and come out whole and in order) and sv106 (two lives of the service in separate processes: the second continues the first's positions); kk-cli mc47 (defaults, forwarding, eight malformed argument shapes refused before the service); the golden tool list regenerated and reviewed; the live suite 59/59 (stages from queued to approval, no detail, nothing new on a second ask, a bad position refused). 11 mutants caught; one (legacy events listed) has no test, because no store with old events exists in the suite.
- Not built: MCP `notifications/progress` for a long call and resource subscriptions (D-D09 stays PARTIAL: the feed is the building block, clients that support progress can be given it later); a blocking `review_wait`.

## Progress for agents without a new tool (ledger D-D09, D-D27)
- Decision: the matrix asked for a blocking `review_wait` on top of the SDK. A new tool changes the published catalog, the leases and every client's tool list for something one optional argument gives: `review_events` now takes `wait_seconds` (0 to 25) and is then a long poll over the existing cursor feed. Nothing new can be seen through it: it still returns stage names and times only.
- Evidence: kk-cli mc92 (answers at once when there is news and asks the service once; with nothing new it asks about every 400 ms for the time given and answers with an empty list; no wait means no delay; -1, 26, "5" and 1.5 are refused before the service is asked), the golden tool list regenerated for the one new argument, the whole MCP suite (59 checks plus the official-SDK client) still passes; 6 mutants: 5 caught, 1 equivalent (the second cap on the wait, which the argument check already enforces).
- Not built: MCP `notifications/progress` for a call that is running (the review is a separate job, not the call), and resource subscriptions for pushing changes. D-D09 and D-D27 stay PARTIAL for those.

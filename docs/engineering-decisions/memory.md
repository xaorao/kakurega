# Memory (registry rows G51-G54, G57, N14; G58 later)

## Target experience
Kakurega remembers what the user wants remembered, can say why it remembers it and since when it is true, never hands a memory to a route that is not allowed to see it, lets the user correct it without losing the history, and when the user says forget, the text is gone from disk and cannot come back by itself.

## Strongest references and what was read
- Anamnesis (Apache-2.0, commit 9d89436, `private-ai/ghast-ai/Anamnesis`): read `GOAL.md`, README, the store migrations 0001 (records, FTS5 with triggers), 0007 (tombstones keyed by the source's natural key so a re-import cannot resurrect a forgotten record) and 0009 (user overlays kept apart from derived data). NOT read: the 14 adapters, the hybrid search and packer (about 2000 lines), the MCP server. Its stance is an interoperability bridge that never edits sources, which is the opposite of ours, so no code is adopted; ideas adopted: tombstone that blocks resurrection, provenance on every record, overlays separate from derived data.
- ghast-memory-os (Apache-2.0, `src/kernel/safety.ts`, `temporal-validity.ts`, `retention.ts` skimmed): ideas adopted: secret-like content never becomes long-term memory; sensitive memory hidden from ordinary context; supersession (`supersededBy`); validity windows. Its date extraction engine (multi-language regex) is not adopted: validity is set explicitly by the user or the kernel, not guessed from prose. NOT read in full: reconstruction, consolidation, gym, retrieval packing.
- Weaknesses to beat: both keep forgotten text recoverable from storage pages or FTS shadow data unless carefully cleaned; neither labels memories for a privacy kernel. Ours: SQLCipher vault with secure_delete and WAL truncation, FTS delete, tombstone as a keyed hash (no plaintext), and a label on every memory enforced at recall.

## Chosen approach
New crate `kk-memory` on the encrypted vault: `memories` table with label (level, compartments, integrity, unknown-sensitivity), validity window, subject, reason and source, status (active, superseded, forgotten), FTS5 over the text; `memory_events` audit without plaintext for forgets; `tombstones` keyed by HMAC of the normalised text. Recall takes the caller's clearance label and an as-of time; memories above the clearance are not returned and not counted.

## Quality criteria (acceptance tests me01-me12 in `crates/kk-memory/tests`)
Label gate (including unknown sensitivity as Restricted); time validity both directions; correction keeps history; forget leaves no plaintext in the database file or WAL; tombstone blocks the same text in any casing or spacing and stores no plaintext; secret-like text refused; duplicates not added; FTS syntax in a query cannot error or widen results; limits and control characters refused; reopen with the key works and a wrong key fails.

## Not covered by this component yet
Semantic (vector) recall, memory import (G55), conflict alerts (G56), encrypted backup and recovery flow (G58, the vault has `backup_to`), automatic capture from reviews, UI.

## Update (capability matrix E, M11): notes for a review
A review no longer gets the 50 newest notes regardless of the task. It gets up to 25 notes within a 24 KiB budget: first the notes that match words from the project folder name and the recipient (recall per word, label-filtered in the query), then the most recent to fill the rest. Each note carries `Included because:` so the owner and the agent can see why it is there; labels and the kernel's clearance rules are unchanged. Test sv25 (mutation: matching switched off fails it). Not done: vector recall, hybrid ranking, and choosing notes from the actual file list (the list is only known inside the runner).

## Project-scoped conversations (recovery of the "project-scoped memory" row)
A private chat can be about a project. The request carries an optional `project` (a folder name, 1 to 80 characters, no control or direction characters, no path separators); the service offers the notes that apply everywhere plus that project's notes, never another project's. Without a project only the everywhere notes are offered, as before. A kept conversation stores its project: a message without one keeps it, a message naming another moves the conversation there, an empty name clears it. Stores made before this gain the `sessions.project` column on open, rows intact.

- Terminal: `/project` shows it, `/project NAME` sets it, `/project none` clears it. On start it is the folder of the nearest repository above the working folder, and none outside a repository. The status line and each reply line say which project was used.
- Web: a "Project (optional)" field on the chat screen with an explanation; a kept conversation restores it.
- Source: Anamnesis keeps a four-way label per record and cannot separate two projects; OpenCode binds each session to a project found from the directory. See the trace row for the reading depth.
- Tightened while doing this: a project name may hold no control character at all. Before, the shared text check let a tab or a line break through, which would break the inline display of a note's project.
- Not done: project identity is still the folder name; two clones with the same folder name share notes. A repository-derived id (as OpenCode does) would fix it and needs a migration of existing notes. MCP exposes no notes; Telegram chat has no project.

## Near-duplicates (recovery of the "memory de-duplication" row)
- **Suggestions.** A suggestion from a review is dropped when it says almost what a saved note, or another suggestion of the same review, already says. Two texts now count as the same claim only if their numbers and yes/no match AND, after lining their words up in order, every word left over is a small word or a near-identical spelling (a plural, a typo) of one left over on the other side. A word that merely moved never counts. Before this, the wording check was order-blind, so "Prefer spaces over tabs" was hidden as a duplicate of "Prefer tabs over spaces" and the owner never saw the changed preference. A synonym ("kept" for "stored") or an added content word is shown as a new suggestion: a duplicate asked twice costs a click, a hidden changed fact costs a wrong note.
- **The owner's view.** Memory screen (a collapsible section), terminal `/similar`, `GET /api/memories/similar`. Read-only: nothing is merged, forgotten or changed. The newest 200 notes the owner may see are compared and the answer says how many; each group is anchored on its newest note and holds only notes that match it directly; notes for different projects are never compared with each other; notes of fewer than four words are skipped.
- **Sources.** Anamnesis builds the report with SimHash, banded hashing, Hamming and Jaccard limits and union-find, which can chain two unrelated notes into one group and is blind to word order. Hermes de-duplicates by exact string only.
- **Found while testing: a memory backup lost notes.** The library clamped every "list notes" request to 200, and the JSON memory backup asks for everything, so an export from a store with more than 200 notes silently dropped the older ones. Fixed (me37, and sv59 exports 210 notes and restores 210 into a fresh store). The encrypted whole-store backup copies the databases and was not affected. NOT VERIFIED: whether any earlier JSON export from a real store was truncated; check any backup file you made before this fix for its note count.


## Recall quality on a published benchmark (LongMemEval, measured)

- **Why.** The merge of the three rankings was tuned on toy examples. A published retrieval benchmark can say whether it finds the right memory among thousands of chat turns, and whether the shipped numbers (meaning may add 5 notes, equal weight) are good.
- **Source (VERIFIED by reading).** LongMemEval, Di Wu et al., MIT, commit 9e0b455: `README`, `src/retrieval/run_retrieval.py`, `eval_utils.py`, `print_retrieval_metrics.py` read in full for the corpus rule and the metrics. Data: the cleaned `longmemeval_s` set (dataset card licence MIT), downloaded to `target/recall-bench/` and never committed. LoCoMo was rejected: CC BY-NC 4.0 is non-commercial.
- **Protocol (copied from the reference).** Corpus is the user turns of the history sessions; the query is the question; the right answer is the turns marked `has_answer` in the answer sessions; abstention questions and questions with no such turn are skipped; session-level recall (any, all) at 5 and 10, NDCG at 10 with the reference formula, and turn-level recall. Ports of the metrics are in `crates/kk-cli/src/recall_bench.rs` (ignored test `recall_benchmark`, run with `KK_RECALL_SAMPLE` pointing at a sample made by `scripts/recall-bench-prepare.py`).
- **Sample.** 275 questions chosen by a fixed content-hash order, equal numbers per question type (60 each; 30 preference, 5 assistant), 67,198 user turns. 105 questions are for choosing settings, 170 are held out and only reported. Real embedding model: `nomic-embed-text` through Ollama. The store refused 182 turns (too long or empty after trimming); none of them held evidence.
- **Setting choice.** 61 settings (meaning cap 5/10/20/50, closeness 0.35 to 0.60, meaning weight 1/2/4) were scored on the 105 development questions only. The shipped setting was kept unless another beat it by 0.01 on session all@10, then any@5, then NDCG@10.
- **Result on the 170 held-out questions (session level, higher is better).**

| | any@5 | all@5 | any@10 | all@10 | NDCG@10 | turn all@10 |
|---|---|---|---|---|---|---|
| keywords and similar wording only | .935 | .782 | .947 | .876 | .520 | .718 |
| as shipped before (cap 5, weight 1) | .976 | .876 | .994 | .929 | .593 | .806 |
| chosen (cap 10, weight 4, closeness .5) | .988 | .924 | .994 | .947 | .642 | .859 |
| plain meaning search, no merge | .988 | .918 | .988 | .959 | .680 | .865 |

- **Read honestly.** Meaning clearly helps over keywords (most on preference and multi-session questions). The chosen setting beats the old one on every aggregate number; the largest gain is multi-session questions (all@5 .650 to .825, 40 questions). One preference question out of 10 moved from found to not found at the top 5 (it is found by rank 10). Plain meaning search still has a better NDCG than our merge (.680 against .642), so the merge is not yet best; what the keyword rankings add is exact-term recall on questions that name a thing, which this benchmark rewards little.
- **Built.** `MEANING_ONLY_CAP` 5 to 10, new `MEANING_WEIGHT` 4.0, `Memories::set_meaning_cap`, `set_meaning_weight`, `fuse::fuse_weighted` (a missing, negative or non-finite weight counts as 1, above 10 is clamped to 10, weight 0 drops a list and the notes only it found). Tests me30, me31, fu07, fu08; eight mutants each fail a test.
- **Not measured (NOT VERIFIED).** Wrong notes shown (false positives and precision); short fact-style notes (the corpus is chat turns); other embedding models (a model with a different score spread may want another closeness); the effect on the review prompts that use recall. The benchmark is recall of the right turn, not answer quality.

## Owner-confirmed merge of look-alike notes (row 31)

- **Target experience.** From the list of notes that say almost the same thing, the owner keeps one and merges the others into it. The merged notes disappear from lists, recall and the assistant, are kept word for word, and can be brought back. The owner decides every merge; nothing happens by itself.
- **Source (read by me).** ghast-memory-os (Apache-2.0, `private-ai/ghast-ai/ghast-memory-os`) `src/kernel/consolidation.ts` (607 lines, all but the stopword list) and `src/runtime/create-memory-os.ts` 4960-5130 (the apply path, PART; the rest of that 6453-line file NOT READ). What it does: eligible notes exclude archived, boundary and person kinds, anything not normal-sensitivity, anything secret-like or routed to a person; duplicates are same-kind notes whose normalised text is equal or where a text of at least 12 characters is contained in the other, plus a tag overlap of at least 0.6; the survivor is the highest confidence, then newest; the others are archived, never deleted, with a pointer to the survivor; a model-written summary may retire its sources only if it covers them losslessly, and is otherwise kept as an extra lower-trust note.
- **Decisions.** ADAPT the idea of archive-not-delete with a pointer to the survivor. REBUILD the grouping: ours is the existing order-aware look-alike report (a swapped meaning or a changed number is never grouped), which fixes Ghast's weakness that one note merely containing another's words is joined to it. EXCLUDE automatic merging and model-written summaries: here the owner chooses the survivor and no words are generated, so nothing can be said that was never said. BUILD what Ghast's source does not show: undo, a list of everything merged, and forgetting the kept note also forgets what was merged into it.
- **Behaviour.** `merge(keep, others)`: 1 to 8 others, deduplicated, none equal to the kept note; every note must be active, readable at the caller's clearance and in the same project, else the whole merge is refused and nothing changes; an unreadable note looks like a missing one. A merged note has status `merged` and `merged_into`; its meaning vector is removed. `unmerge` restores it (and a recall embeds it again). A note merged into one the caller cannot read is not listed. A merged note cannot be corrected or merged again. Forgetting the kept note forgets the merged ones (they are deleted and their wording is blocked from returning). Events record counts and ids only.
- **Evidence.** kk-memory me32-me40 (52 tests), service sv70-sv74, browser e2e 204/204 (merge, list, bring back, axe, screenshot read), 21 + 5 + 5 mutants caught; two first survived (the refusal message, vector cleanup) and led to stronger tests. One test found a real leak while being written: a readable note merged into a restricted one would have revealed that the restricted note exists; fixed.
- **Not built (owed).** Terminal (`/similar` has no merge), a model-written summary of a group with a lossless-coverage rule, entity clusters (notes about one person or project), access counts. The JSON export of notes leaves merged notes out (the encrypted backup keeps them). Merge of more than eight at once takes repeated merges.

## Freshness in recall (ledger E-M13)
- Reference read in full: ghast-memory-os `src/kernel/retention.ts` (d0a9426, Apache-2.0, 184 lines). Its score is 0.6 recency (half-life per kind: fact 180 days, preference 365, project 90, trajectory 45) + 0.2 confidence + 0.1 log recall count + 0.1 reinforcement, with dormant below 0.25 and archive after 180 dormant days; Hermes' curator archives, never deletes, pinned exempt (matrix M13).
- Taken and changed: only the ranking part. Our notes have no confidence or reinforcement signal, so those two terms are not invented: freshness is 6 parts recency and 1 part use (the same 0.6 : 0.1 ratio). Half-lives: 90 days for a note kept for a project, 180 for one that applies everywhere (project and fact in the reference); the reference's other kinds do not exist here. Recency counts from the last use, or from when the note was written if it was never used. Use is log-scaled and full at 20 uses, so a note cannot make itself permanent. The owner's standing orders are not notes and do not decay.
- How it ranks: a note's match score is lowered by up to 5% in proportion to its staleness (`FRESHNESS_SPAN`), and the list is re-sorted. Measured on the merge's scores this moves a note about three places near the top and further down the list, and never a clearly best match (tests me60–me62). The extra effect of many uses over one use is about half a percent of the score, below the gap between neighbouring places, so it cannot reorder two notes that sit next to each other; only a note's last use (a large effect) does. A test that expected it to (me63 as first written) failed one run in three, was removed, and me63 now tests only that the count is kept. A first attempt added a freshness list to the merge with a small weight; it could not even break a tie between two equal matches, because the merge gives tied notes different places, so it was replaced.
- Use records: `memory_use(id, last_at, uses)` is written only when notes were given to the model for a chat (`record_use`, kk-service), never by `recall` itself (recall stays read-only for MCP and reviews). Unknown ids are ignored, at most 50 per call, and a forgotten note's record is deleted with it (a test reads the table). The record holds an id, a time and a count and no text.
- Not built here: dormant status, archiving and pinning (built later, see "Dormant notes, archive and pin" below); the reference's outcome reinforcement and confidence annealing are excluded because no such signal exists in our data (inventing one would be a guess). The half-lives are the reference's and are NOT tuned on our data. Reviews (kk-review) recall without recording use.
- Evidence: kk-memory rt01–rt03, me60–me63, kk-service sv109; 11 mutants caught (one needed a new test).

## Notes a newer secret detector matches are held back (ledger E-M16)
- Reference (matrix M16, read as recorded there): LibreChat re-applies the current policy when stored memories are read (`protection.ts` 98-110); Hermes scans every add and patch; ghast-memory-os never stores secret-like text. Ours already refused secrets at write time with the shared detector (`kk-secrets`). The gap: a note saved before a rule existed stays in recall forever.

## Dormant notes, archive and pin (ledger E-M13 and G-GH-52)
- Gap (VERIFIED): memory only grows. Recall already ranks a long-unused note a little lower (E-M13's freshness nudge), but the owner has no way to see which notes have stopped being useful, or to retire one without destroying it (forgetting is permanent).
- Reading (by me): Hermes `agent/curator.py` (commit 29a61cb7, MIT) lines 1-60 and 209-283: it moves skills active, then stale after 14 days, then archived after 30 days from their last activity or creation; pinned items bypass every transition; archiving is recoverable and never deletes; an item with no use record is anchored at first sight, "not at epoch"; a never-used item younger than the stale threshold is never archived ("absence of evidence"); use after going stale reactivates it. Its transitions are automatic and it runs on a schedule. NOT READ: its scheduler and the LLM consolidation pass (lines 300-1214). Earlier: ghast-memory-os `retention.ts` in full (dormant below a 0.25 score, archive after 180 dormant days; ranking formula).
- Decisions:
  1. **Nothing is retired automatically.** A note is only ever proposed as dormant; archiving happens when the owner presses the button. (Hermes archives by itself; these are notes about a person's own life and work.)
  2. **Dormant** means an active, unpinned note whose last sign of life is at least `days` old (default 180, the reference's own archive-after figure; 30 to 3650 allowed). The last sign of life is the latest of: when it was written, when it was last given to a model (the use records), when the owner last said "still true" or restored or pinned it, and **when this store began recording uses**. That last term is the clock anchor: notes older than the use records have no record because none was kept, not because they were never used, so without it every old note would be proposed on the first day. NOT VERIFIED: that 180 days is a good number; it is a default, not tuned on real use.
  3. **Archive** keeps the note whole and reversible: it leaves recall, the lists, the similar and conflict views and every model prompt, but it is still in the encrypted store, in backups, and in what a newer secret detector rescans. **Restore** brings it back and restarts its clock. **Forget** works on an archived note exactly as on any other, and permanently.
  4. **Pin** exempts a note from being proposed. **Still true** restarts the clock without pinning.
  5. Every one of these is an owner action recorded in the note's event history (kind only, never the text), and none changes a note's text, label, validity or source.
  6. Surfaces: the service (`GET /api/memories/dormant`, `GET /api/memories/archived`, `POST /api/memories/{id}/archive|restore|pin|unpin|keep`), the Memory screen of the web workspace, and the terminal workspace (`/dormant`, `/archive`, `/restore`, `/pin`, `/unpin`, `/keep`). Never the MCP server (memory is not exposed there).
- Beats the source on: proposals, not automatic archiving; an honest clock anchor stated and tested; the reason a note is proposed shown (how long since its last sign of life and how often it was used); every action reversible except forgetting.

- Built (E-M13, G-GH-52): `Memories::dormant`, `archive`, `restore`, `archived_notes`, `keep`, `pin`, `unpin`, `is_pinned`, status `Archived`, tables `memory_keep` (pinned, kept_at) and the `use_records_since` anchor; service `GET /api/memories/dormant|archived|pinned` and `POST /api/memories/{id}/archive|restore|pin|unpin|keep` (every action in the signed log by kind and id, never text); the owner's backup carries archived notes under their own list and a restore puts them back archived; a newer secret detector rescans archived notes too and holds a match; remembering the exact text of an archived note brings that note back instead of making a twin. Web: "Quiet notes" and "Archived notes" sections on the Memory screen, a Pin/Unpin button and a "Pinned" mark on each note, plain-words activity labels (English and Hindi). Terminal: `/dormant [DAYS]`, `/archived`, `/archive ID`, `/restore ID`, `/pin ID`, `/unpin ID`, `/stilltrue ID` (`/keep` and `/quiet` already meant other things).
- Evidence: kk-memory me86 to me93 (age order, exact boundary, days bounds, the clock anchor, archive out of recall/lists/counts/dormant, restore restarts the clock, pin and still-true, forget leaves nothing, archived duplicates, detector rescan); kk-service sv135 to sv138; kk-tui tu92 to tu94; browser suite 466 of 466 (10 new checks, real archive, restore, pin and forget through the UI; only the note's age is faked in the quiet list, because the real endpoint needs 30 days); terminal suite 99 of 99 (11 new, against a real service). 17 mutants, all caught (the first forget mutant broke every forget and proved little; redone precisely and caught by me91).
- Limits, stated plainly: the 180-day default and the 30 to 3650 range are NOT tuned on real use. The clock anchor is the time the store was first opened by a version that records uses; older notes cannot be proposed before it plus the chosen days. A restored note and an unpinned note start a fresh clock. Archive is per note: a note's earlier versions are not archived with it. Archiving does not shrink the store or the backups (the note stays encrypted in the vault). The MCP server does not expose any of this (memory is not offered to agents).

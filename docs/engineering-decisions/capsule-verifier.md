# Signed statements, capsule and independent verifier (part of M1-05, tests V, CP, CH)

## Target experience
A recipient with no account and no trust in us opens a capsule in a browser or a terminal and learns, in plain words, what was signed, what is checked, what is not established, and whether anything was changed. Any edit to any byte is reported with a reason.

## References
Treeship `packages/core/src/attestation/` (Apache-2.0, commit da7f8ac): `pae.rs`, `envelope.rs`, `verify.rs` read in full; its Verifier model (trusted key map, all signatures must verify, zero signatures never passes) and DSSE PAE are adopted as ideas. DSSE spec; RFC 8032 Ed25519; the canonical encoding decision D87.

## Approach
- `kk-evidence::dsse`: DSSE envelope with pre-authentication encoding (type-confusion safe), exactly one Ed25519 signature in v1, key id derived from the public key (`ed25519:` plus the SHA-256 of the key, not a claimed label), `verify_strict`, weak and small-order keys refused, payload must itself be canonical (D87), allowed payload types are an explicit list, and the envelope is parsed with the strict parser and must be byte-for-byte canonical (no whitespace, no extra fields, no base64 padding).
- `kk-evidence::capsule`: a capsule is one canonical JSON document: a release statement (recipient, expiry, policy version, every file with SHA-256 and length, assurance level, route, a signed list of what is not established, a keyed source commitment), optional claim statements bound to the release by the digest of its payload, and the attachments. The verifier returns the first failing reason from a fixed order, or an `established` and a `not_established` list. A key can be pinned; if not, the report says the signer comes from the capsule itself.
- Second verifier: `packages/verifier-js`, written separately: its own strict parser (no `JSON.parse`), its own base64url, its own Ed25519 small-order test on the curve (BigInt), WebCrypto for signatures. It is the seed of the browser verifier.

## Results (VERIFIED_BY_RUN)
- 31 shared vectors (generated by the Rust builder, each asserted at generation time): valid, valid with a pinned key, pinned to the wrong key, expired, wrong recipient, flipped signature bit, edited release payload, changed, removed and added attachments, payload-type swap, unknown type, whole capsule re-signed by another key (valid unpinned, rejected when the original is pinned), mixed signers, two signatures, expiry before creation, unknown assurance level, path-traversal file name, duplicate file name, non-canonical signed payload, claim bound to another release, claim citing a file not in the release, missing and duplicate release statements, version change, unknown field, no keys, all-zero key, trailing garbage, trailing newline.
- Rust and JavaScript return the same verdict, the same reason code and the same signer on all 31. The generator is deterministic (a test regenerates the file and compares).
- 13 mutations (7 in Rust, 6 in JavaScript: digest check, claim binding, canonical capsule check, key pinning, signature count, weak-key check, signed type binding, signature check) were each applied and each caught.
- Base64url codec: strict (no padding, no whitespace, no non-zero trailing bits), tested on all lengths up to 69.

## Not covered
WASM build of the Rust verifier and the browser UI around the JS one; the keyed source commitment itself (its creation and the B1 binding claim are built with the release pipeline); Merkle inclusion proofs and transparency anchoring; key rotation and revocation; signing key custody in the vault; a very large capsule performance test; fuzzing the capsule parser with mutated bytes; second-signature (co-signer) policy.

## Model receipts (NEAR loop step 3)
- The release's `assurance` may carry `route_receipts`; both verifiers check them (shape, kind, key, signature, duplicates, cap) in the same order and agree on 45 shared vectors, 14 of them new. See `near-route.md`.

## Finding: a capsule's key list was not authenticated (fixed)
- Found by a hostile test of the registration ticket: a capsule with one byte of its `keys` entry changed still verified when the reader pinned the signer, because the pinned key replaced the list and the list was then never looked at. Without a pin, a second, unused key could be appended and the capsule stayed valid. No signature could be forged this way, but the same signed content could exist as many different files, each valid, which breaks anything that names a capsule by its file digest (the NEAR registry does).
- Fix, in both verifiers: the key list must be exactly the one key that signed (`key_list` otherwise). Six shared vectors added (52 in all): an unused second key with and without a pin, another valid key under a pin, the signer listed twice, an empty list under a pin, 32 bytes that are no key under a pin. No earlier vector's verdict changed. Mutants: the rule removed, count only, identity only in Rust; removed and count only in JavaScript; 5 of 5 caught.
- The reason is shown in words on the web, on the standalone page and in Hindi (unread by a person, like the rest of the Hindi text).

## Sharing one finding with a proof (plan item 4; Aftercall's "share one line" taken further)
Target: the owner hands one finding of a delivered review to someone who was not its recipient. That reader can check, offline and alone, that the finding is part of the signed release, can re-run it, and learns nothing else about the release.
- Reference: Aftercall shares one line of a result with a proof (REPORTED from its README; its code was not read for this). The construction here is the hash tree of RFC 6962 with the audit-path check of RFC 9162 section 2.1.3.2, read from the RFC text.
- Why a new statement and not the capsule's own: the capsule's signed release statement lists every file's name, size and plain SHA-256. Showing it to a third party would reveal those, and a plain hash of a short text can be confirmed by guessing. So the signer signs a second, short disclosure statement: the capsule's digest, the release statement's digest, and the root of a hash tree whose leaves are the files, each hashed with its own secret salt (`SHA-256(0x00 || salt || len(name) || name || content)`). A share carries that statement, the shared files with their salts, and each file's path to the root.
- The salts come from a secret the owner's service holds and the capsule's digest (HMAC-SHA-256, checked against an independent implementation), so a share can be made at any time, is the same bytes every time, and nothing in one capsule's share helps against another.
- Each finding now also has its own index entry in the capsule (`meta-N.json`). A share of finding N holds its text, reproducer, expected output, the minimal sample it was checked on, that entry and the check script; `kaku verify FILE --out DIR` writes them into a new folder with a list of findings that holds only the shared one, and `python3 DIR/run-check.py` re-runs it.
- Code: `crates/kk-evidence/src/share.rs`; `packages/verifier-js` `verifyShare`; the public check page (a `.kks` file dropped on it; shared files shown as text only); service `GET|POST /api/jobs/{id}/share` (owner's session only, the share is verified before it is handed over, and making one is written to the signed log); `kaku share JOB FINDING`; "Save a share" on a delivered review's Release tab.
- Evidence: kk-evidence sh01 to sh06 (every leaf of every tree size up to 33, a leaf passed off at another place, every part of a share changed, a forger's own statement, determinism); 59 shared vectors in `fixtures/share/vectors.json` on which the Rust and the JavaScript verifier agree, verdict and reason; 16 mutants of the verifier: 15 caught, one equivalent (a second guard against an over-long path, which a changed hash already refuses). kk-service sv248 (nothing of any other file in the share by name, content or plain hash; not the recipient; a capsule changed on disk shares nothing). `tests/e2e/share_finding.py` 24 checks with the real binary, including the reader re-running the finding from the share alone. `tests/e2e/share_web.mjs` 8 browser checks ending on the public page opened from disk with no network. `tests/e2e/verifier_page.mjs` 9 more checks (markup inside a shared file is shown as text and does not run).
- What a share shows: the shared files, the signer's key, the two digests, and how many files the release has. What it does not establish is printed with every check: nothing about the other files, not that the finding is true, not who the release was for.
- Limits: anyone who also holds the full capsule can tell that a share came from it (the digest is in both). The number of files in the release is visible. The sample of project files a finding was checked on is part of that finding and is shared with it. The list of findings written by `--out` is made on the reader's computer and is not signed; the files it names are.

# GitHub connector, read only (backend)

## The four lines
1. Experience: the owner connects GitHub once by typing a short code on GitHub's own page (no password, no secret pasted into this program), then asks about their repositories, issues, pull requests and files in chat; anything taken from GitHub is clearly labelled as written by other people, a key or an order planted in an issue never reaches the model, and signing out is one action that says plainly what is left to do at GitHub.
2. References: OpenClaw `src/agents/github-oauth-client.ts` (MIT, commit f38495f7d, read in full, 496 lines); goose `crates/goose/src/providers/oauth_device_flow.rs` (Apache-2.0, commit 71dd9a9, lines 1-330 read, the rest not read); MCP Rust SDK `crates/rmcp/src/transport/auth.rs` (MIT and Apache-2.0, commit d66a74d, lines 270-414 and 2470-2624 read, the rest not read); IronClaw `crates/extensions/packages/github/` (MIT or Apache-2.0, commit b0b999d): `manifest.toml` first 80 lines, `wasm-src/src/request.rs` and `api/contents.rs` in full, `validation.rs` lines 1-200, `response.rs` lines 1-200; not read: `lib.rs`, `dispatch.rs`, `api/issues.rs`, `api/pulls.rs`, `api/search.rs`, the schemas and prompts. House code read in full: `kk-cli/src/handoff.rs`, `near.rs`, `outside.rs` (client construction), `kk-service/src/service/handoff.rs`, `swap.rs`, `breakit.rs`, `attachments.rs` (lines 1-330), the upload path in `service.rs` (`attach_bytes`, `attachment_get`, the file part of `chat_context`), `kk-fetch/src/lib.rs` transport (lines 1-60, 170-360, 680-830).
3. Approach: device flow with no client secret (a public client), one poll per call so the service and the screen schedule it, the token pair in one private file, an in-process single-flight refresh with compare-and-swap on write, a small fixed set of reads, and attachments made through the same function as an uploaded file. The HTTP client is ureq 3 (already a dependency of kk-cli) built the way `outside.rs` builds its client: no redirects, no proxy, a 30 s overall timeout, plus https only for the real hosts. No new dependency.
4. Quality bar: OpenClaw's response validation (the strongest found) matched or exceeded; every documented device-flow error has a plain-words outcome; the token never leaves the token file except in the Authorization header to the API host; every safeguard has a test that fails when it is broken.

## Official facts relied on (VERIFIED by fetching the page, this session)
- https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps: `POST https://github.com/login/device/code` (client_id, scope), `POST https://github.com/login/oauth/access_token` (client_id, device_code, grant_type `urn:ietf:params:oauth:grant-type:device_code`); no client secret for the device flow; JSON only with `Accept: application/json`; device code 40 characters, user code 8 with a hyphen, expires_in 900 by default, interval minimum; `slow_down` adds 5 s and its answer carries the new interval; errors authorization_pending, slow_down, expired_token, unsupported_grant_type, incorrect_client_credentials, incorrect_device_code, access_denied, device_flow_disabled; verification page https://github.com/login/device.
- https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens: user tokens last 8 h (28800), refresh tokens 6 months; refresh is `grant_type=refresh_token` with client_id, no secret when the token came from the device flow; refresh tokens are single use and the old access token stops working; `scope` is always empty for a GitHub App; expires_in and refresh_token are omitted when the app's tokens do not expire. The page lists no refresh error codes: `bad_refresh_token` is REPORTED (OpenClaw's list), `invalid_grant` is the RFC 6749 code; both are treated as "sign in again".
- https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api: primary limit is 403 or 429 with `x-ratelimit-remaining: 0` and `x-ratelimit-reset` (epoch seconds); secondary limit is 403 or 429 with `retry-after`, otherwise wait at least a minute.
- https://docs.github.com/en/rest/repos/contents: files up to 1 MB come with content; 1-100 MB only through the raw media type (`encoding: none` otherwise); `ref` query parameter; API version 2026-03-10.

## What was built
- `crates/kk-cli/src/github.rs`: client id check (`Iv1.`+16 hex, `Iv23`/`Ov23`+16 alnum); fixed hosts with the loopback-only test override `KAKU_GITHUB_TEST_BASE=http://127.0.0.1:PORT` (any other value turns the connector off and says so); device start and poll with strict answer checks; the pending device code in process memory only, one poll at a time and none before the interval; the token file `github-token.json` (0600, temporary file and rename, refused when group or other can read it or when it is a link); refresh five minutes early and once after a 401, under one process-wide mutex, written only if the file is unchanged; a rejected refresh removes the file; sign-out removes it and says how to revoke at GitHub; reads whoami, repos, issues, pulls, issue (with up to 50 comments), file (text only, 1 MB), search (inside one repository, `repo:`/`org:`/`user:` refused); every answer capped (16 KB sign-in, 2 MB reads) and every text capped (titles 300, issue body 100,000, comments 20,000 each and 100,000 together, files 200,000 characters), with `cut` flags; rate limits reported with `retry_at`, never retried.
- A GitHub App asks for no scope (its permissions come from the app); an OAuth App asks for `read:user` only, so it reads public repositories only and cannot write.
- Changing the client id signs out: a token belongs to the app that issued it (the rmcp rule that a stored token is never refreshed under another client).
- `JobRunner` methods with "not available" defaults and their `ReviewRunner` delegation (data folder = the folder the route choice is kept in).
- `crates/kk-service/src/service/github.rs`: the six endpoints; keys `access_token`, `refresh_token`, `device_code`, `token` are dropped from every runner answer at any depth, and a sign-in answer that still holds anything shaped like a key is not shown at all; reads are labelled `untrusted: true, source: github`; `attach: true` on an issue or a file calls `attach_bytes`, the function an upload uses; log kinds `connector.client_set`, `connector.sign_in_started`, `connector.connected`, `connector.sign_in_ended`, `connector.signed_out`, `connector.read` (action and item count), `connector.read_refused` (action), `connector.attached` (action), subject `github`, never a repository, title, account or token.

## Endpoints (all need the owner's session; POST needs the CSRF header)
- `GET /api/connectors/github/status` -> `{available, problem, client_set, client_id, client_kind: "github_app"|"oauth_app"|null, connected, account: {login, id}|null, scopes, access_expires_at, pending: {user_code, verification_uri, expires_at, expires_in, interval, next_poll_in}|null, read_only: true, test_hosts, note}`.
- `POST .../client {client_id}` -> the status plus `signed_out`.
- `POST .../start {}` -> `{user_code, verification_uri, expires_at, expires_in, interval, next_poll_in}`.
- `POST .../poll {}` -> `{state: wait|waiting|slow_down|authorized|expired|denied|disabled|failed, done, message, interval?, next_poll_in?, account?, scopes?}`.
- `POST .../signout {}` -> `{signed_out, connected: false, message, revoke}`.
- `POST .../read {action, owner?, repo?, number?, path?, ref?, state?, page?, query?, attach?}` -> the read's data plus `action, source, untrusted, note, rate: {remaining, reset_at}`, and `attachment` (the upload summary with `id` and `flagged`) when attached.
- Errors: `{"error": {code, message, retry_at?}}`; NOT_AVAILABLE/CONFIG 503, NO_CLIENT/SIGNED_OUT/NO_SIGN_IN/DEVICE_FLOW_DISABLED 409, BAD_CLIENT/REFUSED/NOT_A_FILE/BINARY/TOO_LARGE/FORBIDDEN 422, RATE_LIMITED 429, NOT_FOUND 404, network and answer problems (UNREACHABLE, BAD_ANSWER, ANSWER_TOO_LARGE, REFRESH_FAILED, FAILED) 502.

## GitHub App or OAuth App
| | GitHub App (recommended) | OAuth App |
|---|---|---|
| Read-only private repositories | yes: grant Contents, Issues, Pull requests, Metadata as read-only | no: private repositories need the `repo` scope, which can also write |
| Which repositories | chosen by the owner at install | all the account can see |
| Token lifetime | 8 h with a single-use refresh token | does not expire unless revoked |
| Device flow | must be enabled in the app's settings | must be enabled in the app's settings |

Recommendation: a GitHub App with read-only permissions and Enable Device Flow on. It is the only way to read private repositories without a token that could also change them, and its short-lived tokens limit what a stolen token file is worth.

## Limits and NOT TESTED
- BLOCKED: a real GitHub App. No client id has been supplied by the owner; everything above ran against the loopback stand-in. Needed: a GitHub App client id with Device Flow enabled, then one real sign-in, each read, an 8 h expiry and refresh.
- The compare-and-swap is a read-compare-rename, not an atomic file lock: two `kaku serve` processes on one data folder could still race in the instant between the compare and the rename (the in-process mutex covers one process).
- The pending sign-in is lost when the service restarts (by design: the device code is never written). The service does not poll on its own; the screen calls `poll` at `next_poll_in`.
- Pull request review comments (on lines of code) are not read; `issue` returns the conversation comments only. Files over 1 MB are refused rather than fetched raw.
- A connection to github.com is not pinned to a checked address as `kk-fetch` pins page fetches; the hosts are fixed and TLS certificate checks bind them.
- GitHub Enterprise hosts are not supported.

## The screen (added after the backend)
- Skills has a "GitHub (read only)" card: paste the client id of your own GitHub App, connect (the code to type at github.com is shown and the page asks again by itself when GitHub allows), read an issue, pull request or file by repository and number or path, and attach it to the next chat message. The attachment is the one the service made through the upload parser, so the lines that hold a secret or read like orders are already marked as held back; the card says how many.
- Evidence: `tests/e2e/github_web.mjs`, 13 browser checks against the stand-in GitHub (refused client id, sign-in without a reload, a repository name with `..` cannot be asked for, the planted key and order counted as held back, the chat opening with the attachment, the token in its own file and in neither the page nor the service's output, sign-out).
- NOT TESTED: the real github.com (BLOCKED until the owner's client id exists).

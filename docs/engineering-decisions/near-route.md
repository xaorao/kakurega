# The NEAR route: a model on confidential hardware that gives no answer until both proofs verify (NEAR loop, step 2)

## Target experience
1. Private data can be sent to a model that runs on NEAR AI Cloud's confidential hardware, and the owner and any recipient can see why that was safe: the hardware proof checked out before the request, the request travelled encrypted to the model's own key, and the answer came back signed by the model's hardware over exactly the bytes exchanged. If any part fails, nothing is given to the owner.
2. Strongest references: NEAR's official inference SDK (this route is built on it), and the rival entries' verifiers that separate the gateway's signature from the model's.
3. Approach: `kk_near::route::NearRoute` implements the kernel's `Route`. The kernel, not the route, decides which data it may receive (`route_ceiling`: restricted only because the reply key is bound).
4. Quality criteria: no request to an unverified deployment; a gateway-signed answer is not accepted as the model's; a tampered or wrongly signed answer is held back; every answer leaves a receipt; errors are named; nothing is retried that could double a charge.

- Live check of the upgrade, keyless, against the real NEAR endpoints: the four attestation tests of `kk-near` pass on 0.3.0 (VERIFIED by run).

## Built
- `kk-route`: `RouteError::NotVerified`, a `receipt` on `RouteEvidence`, `neutralised` (the one text clean-up every model route applies), `Route::reply_key_bound` and the kernel's `route_ceiling` (see `near-attestation.md`).
- `kk-near::route::NearRoute`: before the request, `verify_deployment` (gateway attestation with a fresh challenge and TLS binding, model attestation with the product's policy: up-to-date patch level and a verified GPU report by default); the request body is OpenAI-shaped, with tools, and encrypted end to end by the SDK; after the answer, `verify_response` and the check that the signature kind is the model's (`provider_tee`), not the gateway's; the answer's fields are decrypted by the SDK; tool-call arguments are read as data; a receipt (completion id, signature kind, signer, signed text, signature, deployment: gateway and model patch level, GPU check, compose and OS image hashes, the time) is kept for `evidence()`.
- HTTP statuses are named (401 and 403, 402, 404, 413, 429 and 5xx busy); a failed proof is `NotVerified` and is never retried.
- The layer of `kk-near` moved from 1 to 2 because it now depends on `kk-route`.

## Step 3: the receipt in the capsule, checked by both verifiers
- A capsule's `assurance` may now carry `route_receipts` (1 to 64): for each answer a verified model route gave during the review, the completion id, the signature kind (always `provider_tee`), the model enclave's Ed25519 key in hex, the signed text `MODEL:SHA256(request):SHA256(answer)` and the signature. The broker collects them per answer (only from a verified route, at most 64), the job carries them, the snapshot keeps only the model's own well-formed ones, each answer once, and the capsule builder embeds them.
- Both verifiers, written separately (Rust `kk-evidence`, JavaScript `packages/verifier-js`), check every receipt in the same order: shape, kind (a gateway-signed receipt is refused, `receipt_kind`), key (invalid or small-order is refused, `receipt_key`), then the signature over the exact text (`receipt_signature`); no duplicate answer, at most 64, not an empty list. 14 new shared vectors (45 in all), generated by Rust and asserted in both languages: one and two receipts, a flipped signature, changed signed text, gateway kind, a weak key, a valid key that is not the signer, an extra member, bad hex, no hashes, an empty model name, a duplicate, an empty list, a non-list, 65 receipts. 16 of 16 mutants of the receipt checks caught (8 per language).
- What a reader is told: the model signatures verify, with the model, answer id, hashes and signer listed; and NOT established: that a signer key belongs to attested hardware (this needs the quote, checked online by `/proof` in the terminal or the proof panel in Chat), and that a signed answer is the text behind a claim.
- Evidence: `kk-broker` rc01 to rc04 (4 mutants), `kk-service` sn01 (3 mutants), `kk-review` rs08 (a built capsule verifies with its receipts, a forged one breaks it), `tests/e2e/verify_receipts.mjs` (the real `kaku verify` and the browser page on fresh capsules: listed, forged refused with its reason in words, zero console errors). A first draft of the page's text promised a `kaku proof` command that does not exist; corrected to the commands that do.
- Still not built: choosing the NEAR route from `kaku serve`, streaming, a check that the answers in the receipts are the ones behind each finding, and the live signer-to-quote link (needs the key).
- The fake gateway cannot say anything about real hardware: it reads the report data from the quote string itself.

## Step 4: choosing the NEAR route from `kaku serve`
- `kaku serve --route near --near-model NAME [--near-key-file FILE] [--near-url URL]`; the key comes from `NEAR_AI_API_KEY` or from a file of `NEAR_AI_API_KEY=...` lines that only its owner can read (a file others can read is refused with the `chmod 600` advice). The key never appears in an error, a log or the page. A route that is asked for and cannot be made stops the service from starting; it never falls back to another route. `--near-url` must be https (or http to this computer, for a test gateway).
- What goes to NEAR: chat answers (streamed chats arrive whole, after their proof), review jobs and conversation summaries; the readiness check "Model on NEAR AI Cloud" fetches and verifies the proof now. Questions about a project and coding tasks go there too (they were local only at first; reviews already gave the whole project to the same confidential model, so the two agents now follow the review's rule: this computer or confidential hardware whose proof is checked, never a hosted model without one; a project kept on this computer is not read by them; and the signed log records each one as having left before any file is sent, `outbound.agent`, tests sv276 and sv298 with 3 of 3 mutants caught). What stays local: embeddings and model choice. The service treats the NEAR route as not on this computer, so restricted notes stay out of chats, secrets in attachments are withheld and the page names the host.
- Evidence: `kk-cli` rn01 to rn06 (chat reply with its class, the question never in the clear on the wire, route info, a stream, proof failure with no request sent, named service errors that never say "local model", readiness, summaries; 7 of 7 mutants caught), nk01 and nk02 (key file rules, flag rules; 6 of 6 mutants caught, the key never in an error). ## Choosing the route from the app (plan item 7)
- Before: the route was fixed by flags of `kaku serve`; the account key came from an environment variable or a key file named on the command line. A person using the web or desktop app had no way to switch.
- Now: Settings has "Where the model runs". The owner can switch between the model on this computer and NEAR AI Cloud (a model name and the account key), and back, while the service runs. A review that has started keeps the route it started with.
- The key: typed into a password box, sent once to the local service, handed to the runner, and written to one file in the data folder (`near.key`, mode 0600, written to a temporary file and renamed). The service does not store or log it; no reply holds it. A key file that others can read is not used. "Forget the saved key" removes the file and is refused while the key is in use.
- The choice (`route.json`: the route's name and the model, never the key) is used at the next start when no `--route` flag is given; a flag always decides.
- A route that cannot be built leaves everything as it was. Nothing is asked of NEAR when the route is chosen: the hardware proof is fetched and checked at first use and by the proof panel, as before.
- The outside test model is still switched on from the terminal only; in the app it can only be left.
- Code: `crates/kk-cli/src/runner.rs` (`Slot`, `route_options`, `choose_route`), `crates/kk-cli/src/near.rs` (saved key and choice), `crates/kk-service/src/service/swap.rs` (`/api/route/options`, `/api/route/choose`), `apps/web/src/screens/Settings.tsx` (`RouteChoice`).
- Evidence: kk-cli rt01 to rt03; `tests/e2e/route_web.mjs` 19 browser checks with the real binary (switch with a made-up key, the key in one file only and nowhere in the page or the service's output, the choice kept over a restart, back to local with a real answer, forget).
- NOT TESTED: an answer from NEAR after switching in the app (BLOCKED: no account key yet). To be run when the key exists: choose NEAR in Settings, ask a question, open the proof panel.
- Limit: the key file is protected by file permissions, not encrypted with a key from the system keychain.
